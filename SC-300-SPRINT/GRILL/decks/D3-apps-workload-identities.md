# SC-300 Domain 3 — Workload Identities & App Access

> **Exam weight: 20–25%.** Covers planning/design/implementing enterprise app SSO (gallery apps, custom SaaS, Application Proxy), consent framework, provisioning (SCIM), app registrations, application objects vs service principals, delegated vs application permissions, app roles, credentials (certificates/secrets/managed identities), and monitoring (Usage & insights, audit logs).

## Unit 3.1 — Plan and design the integration of enterprise apps for SSO

### Flashcards

- **Q:** What is a CASB? **A:** **Cloud Access Security Broker** — an on-premises or cloud-based security policy enforcement point placed *between* cloud service consumers and cloud service providers, interjecting enterprise security policies as cloud resources are accessed.
- **Q:** What is Microsoft Defender for Cloud Apps (MDCA)? **A:** Microsoft's implementation of a **CASB** that protects data, services, and applications with enterprise policies; supports deployment modes including **log collection, API connectors, and reverse proxy**.
- **Q:** What does Cloud Discovery do, what powers it, and what should you review on its dashboard? **A:** Visibility into **shadow IT** by analyzing your **traffic logs** — snapshot reports come from manually uploaded firewall/proxy logs, continuous reports from MDCA log collectors. On the dashboard check: high-level usage overview, top categories, sanctioned usage share, **top users/source IPs**, App HQ map, **risk scores**, open alerts.
- **Q:** Name key filters available on discovered apps. **A:** App tag (**sanctioned/unsanctioned**), apps/domains, categories, **compliance risk factor** (HIPAA, ISO 27001, SOC 2, PCI-DSS), general/security/legal risk factors, **risk score** (which you can override), and usage statistics.
- **Q:** How do you sanction or unsanction an app in MDCA? **A:** Via the **Cloud app catalog** — a catalog of **16,000+ cloud apps** scored by Microsoft analysts based on **80+ risk factors**; you can customize scores/weights to your organization.
- **Q:** What does the AD FS application activity report tell you? **A:** Which AD FS applications can migrate to Microsoft Entra ID — it assesses compatibility, flags issues, and gives migration guidance. Found under **Microsoft Entra ID > Enterprise applications > Activity > Usage & insights > AD FS application activity**; it lists AD FS apps with an **active user login within the last 30 days**.
- **Q:** Which roles can view AD FS application activity data? **A:** Global Reader/Administrator, **Report Reader, Security Reader, Application Administrator, Cloud Application Administrator**.
- **Q:** What are the three migration statuses in the AD FS application activity report? **A:** **Ready to migrate** (fully supported as-is), **Needs review** (some settings migrate, others need review), **Additional steps required** (unsupported settings — can't migrate in current state).
- **Q:** Which two app types should be migrated off AD FS, and in which order? **A:** **SaaS apps** (procured) and **line-of-business (LOB)** apps (internally developed). Migrate apps using **modern protocols (SAML/OIDC)** first — via gallery connectors or registration; integrate **legacy-protocol** apps using **Application Proxy and/or Microsoft Entra Domain Services**.
- **Q:** How do MDCA app connectors work? **A:** They use provider **APIs** (HTTPS-encrypted) for greater visibility/control; MDCA optimizes around API limits/throttling, so some scans run hours or days. **Multi-instance support applies only to API-connected apps** (e.g., two Salesforce instances).
- **Q:** What capabilities does an API connection enable? **A:** Account information, audit trail, account governance (suspend users, revoke passwords), app-permission governance (**revoke tokens**), data scan (**periodic every 12 hours + real-time** on change), and data governance (quarantine/overwrite files).
- **Q:** What can every user do in Microsoft Entra ID by default regarding apps, and how do you restrict it? **A:** By default **all users can register applications** and **consent to apps accessing company data on their behalf**. Set **Users can register applications = No** (User settings) and/or **Users can consent to applications accessing company data on their behalf = No** (Consent & permissions). Assign the **Application Developer** role to restore those abilities for selected users.
- **Q:** State the ownership rules for application registrations and enterprise applications. **A:** A creator is **automatically the first owner**. **Users AND service principals can own application registrations; only users can own enterprise applications; groups can't own either.**
- **Q:** What is the credential-related risk of app owners and Application/Cloud Application Administrators? **A:** They can **add credentials to an app and impersonate its identity** — the app often has more permissions than the person, making this a potential **elevation of privilege**.
- **Q:** Compare the Application Administrator and Cloud Application Administrator roles. **A:** Both create/manage all aspects of enterprise apps, app registrations, and can consent to delegated and application permissions (**excluding Microsoft Graph**). Difference: **Application Administrator also manages application proxy settings; Cloud Application Administrator does not**. Neither is auto-added as owner of apps they create, and **neither can manage Conditional Access**.
- **Q:** What are the rules for custom app-management roles? **A:** Creating the role definition and assigning it are **separate steps**; a role can be assigned **directory-wide or scoped to a single app registration**. Limits: work only in the **current** app-registrations experience (not legacy), are blocked by the **Restrict access to Entra administration portal** user setting, and assignments appear only on the **All applications** tab (not Owned applications).

### Understand-check questions

1. You suspect unsanctioned SaaS sprawl. Which feature surfaces it and from what data?
   **A:** Cloud Discovery in MDCA — analyzes traffic logs from firewalls/proxies (snapshot upload or continuous log collectors) to expose shadow IT.
2. An AD FS app shows "Additional steps required." What does that mean?
   **A:** Some of its settings aren't supported by Microsoft Entra ID, so it cannot be migrated in its current state.
3. Your Salesforce deployment has separate sales and marketing instances. Can MDCA connect both?
   **A:** Yes — multi-instance support exists for API-connected apps, managed from the same console.
4. A developer needs to create app registrations after user registration was disabled tenant-wide. What do you assign?
   **A:** The Application Developer role — it restores registration rights (and self-consent ability) for its members.
5. Why should you hesitate before granting a helpdesk tech the Application Administrator role?
   **A:** They could add credentials to high-privilege apps and impersonate the app's identity — an escalation beyond their own permissions.
6. Where do users see gallery apps, and which property controls that?
   **A:** My Apps and the Microsoft 365 app launcher; controlled by **Visible to users?** in the enterprise app's Properties (alongside *Enabled for users to sign-in?* and *User assignment required?*).

### Real-world use cases

- **Mid-size retailer, shadow IT cleanup:** Finance teams adopted unknown file-sharing tools. Deployed MDCA Cloud Discovery with firewall log collectors, filtered the dashboard by risk score and compliance certifications (PCI-DSS), sanctioned approved storage apps, and blocked the rest — because discovery precedes control: you can't secure apps you don't know exist.
- **Insurance company, AD FS retirement:** 40+ apps federated to aging AD FS servers. Ran the **AD FS application activity report** (accessed by a Report Reader), triaged apps by migration status, re-pointed modern SAML/OIDC apps to gallery connectors first, and queued legacy header-based intranet apps for Application Proxy — giving one control plane for Conditional Access instead of split on-prem/cloud policy.
- **University IT, delegated app administration:** Central IT was a bottleneck for dozens of departmental apps. Disabled default user registration, assigned **Application Developer** to the dev team, scoped a **custom role** to a single student-portal app registration for a contractor, and assigned **Cloud Application Administrator** (no proxy duties needed) to the SaaS team — reducing Global Administrator overhead while shrinking blast radius.

## Unit 3.2 — Implement and monitor the integration of enterprise apps for SSO

### Flashcards

- **Q:** At what levels can you configure token lifetime policies? **A:** For **all apps in the organization** (default policy), for a **multitenant application**, or for a **specific service principal** — a policy object holds the rules and is overridden by higher-priority assignments.
- **Q:** When would you use Conditional Access sign-in/session controls instead of raw token-lifetime tuning? **A:** Complex cases: unmanaged/shared devices, sensitive info from external networks, high-impact users, critical business apps — CA targets these precisely without touching all apps.
- **Q:** What are optional claims used for? **A:** Developers select extra claims (or change claim behavior) in **v1.0, v2.0, and SAML tokens**. Because v2.0 tokens are deliberately **smaller**, several former claims must now be requested per application.
- **Q:** What is the default user-consent posture in Microsoft Entra ID, and what are the configuration options? **A:** By default all users can consent to permissions that **don't require admin consent** (e.g., their own mailbox) — never org-wide data. Options: **disable user consent**; allow only **verified publishers/tenant apps for classified low-impact permissions** (requires classifying permissions); allow **all apps**; or apply **custom app consent policies**. Microsoft recommends verified-publisher-only to blunt malicious-app consent phishing.
- **Q:** What is risk-based step-up consent and is it on by default? **A:** **Enabled by default**: when Microsoft detects a **risky end-user consent request**, it forces step-up to **admin consent**. It only changes behavior when end-user consent is enabled. Blocked users may see **AADSTS90094**; an audit event logs Category **ApplicationManagement**, Activity Type **Consent to application**, Status Reason **Risky application detected**.
- **Q:** What are the two halves of Microsoft Entra **Application Proxy**? **A:** The **Application Proxy service** running in the cloud, and the **Application Proxy connector** running on an on-premises server — together they securely pass the user sign-on token from Entra ID to the on-prem web app.
- **Q:** What kinds of on-prem apps does Application Proxy support, and what does it replace? **A:** Apps using **Integrated Windows Authentication (IWA)**, **form-based** or **header-based** access, web APIs, apps behind a **Remote Desktop Gateway**, and rich clients using **MSAL**. It replaces **VPN/reverse proxy** for remote access — and is **NOT intended for internal corporate-network users** (performance issues).
- **Q:** Walk through the Application Proxy request flow. **A:** User hits the external URL → redirected to Entra sign-in → token sent to client → client presents token to the **App Proxy service**, which extracts **UPN/SPN** → request goes to the **connector**, which performs any additional SSO authentication on the user's behalf (for IWA apps this is typically **Kerberos Constrained Delegation, KCD**) → app responds back through connector and service.
- **Q:** Contrast OAuth, OpenID Connect, and SAML in one line each. **A:** **OAuth = authorization; OIDC = authentication** (built on OAuth 2.0); **SAML = authentication** — commonly used with federated providers like AD FS in enterprise apps, while **OIDC dominates pure-cloud apps, mobile apps, and web APIs**.
- **Q:** Define app provisioning in Microsoft Entra ID and its headline benefits. **A:** Automatically **creating, maintaining, and removing** user identities/roles in SaaS apps as people join, move, or leave. Benefits: automated provisioning/deprovisioning, data synchronization between systems, group provisioning, access governance/auditing, **brown-field matching** of pre-existing identities, customizable **attribute mappings**, and **alerts + Log Analytics integration**.
- **Q:** How do you distinguish manual vs automatic provisioning support? **A:** Gallery apps supporting automatic provisioning carry a **Provisioning icon**; the supported mode also shows on the app's **Provisioning** tab once added to Enterprise apps.
- **Q:** What problem does SCIM solve and what does the spec define? **A:** Proprietary user APIs differ per app; **System for Cross-domain Identity Management** standardizes a **common user schema** plus two endpoints — **/Users and /Groups** — using standard **REST verbs** (POST/GET/PUT/PATCH/DELETE). Paired with SAML/OIDC federation, SCIM delivers an end-to-end standards-based access solution.
- **Q:** What does the Usage & insights report answer? **A:** App-centric sign-in analytics: **top used applications, apps with the most failed sign-ins, and top sign-in errors per app** — filterable by date range, drillable per day (Identity > Applications > Enterprise applications > Activity > Usage & insights).
- **Q:** Who can read Entra audit logs, and what columns does the default view show? **A:** Security Administrator, **Security Reader, Report Reader, Global Reader** (and Administrators). Columns: date/time, logging service, **category and activity name (what)**, **status (success/failure)**, target, and **initiator/actor (who)**. The Enterprise-applications-filtered view answers: which apps were added/updated/removed, whether a service principal changed, renamed, or **who consented to an application**.
- **Q:** What are My Apps collections and what license do they require? **A:** Groupings of related apps shown as separate tabs in the My Apps portal (myapps.microsoft.com). Requires **Microsoft Entra ID P1 or P2**. Admin collections are managed via **Enterprise applications > App launchers**; a collection **filters** apps the user can already access. Users with P1/P2 can also build personal collections in the portal.

### Understand-check questions

1. A shared kiosk PC accesses a sensitive finance app. Which mechanism limits session length?
   **A:** Conditional Access **authentication session management** (e.g., sign-in frequency) targeting that app/device class — rather than a tenant-wide token lifetime change.
2. Your app's v2.0 token is missing a claim the old v1.0 token had. Fix?
   **A:** Add it via **optional claims** on the app registration — v2.0 trims claims for smaller tokens, so they must be explicitly requested.
3. A user hits "AADSTS90094…only an admin can grant" while consenting. What happened?
   **A:** Risk-based step-up consent flagged the request as risky, requiring administrator approval (or the permission itself is admin-restricted).
4. Remote staff need SSO to an IWA intranet timesheet app without VPN. Design?
   **A:** Install an **Application Proxy connector** on-prem, publish the app, choose IWA SSO — the connector uses KCD to authenticate the user to the backend.
5. A vendor SaaS has no provisioning connector. Options?
   **A:** Manual provisioning (portal/spreadsheet) — or ask the vendor to implement a **SCIM 2.0** endpoint exposing /Users and /Groups so Entra can drive it.
6. Auditors ask "who consented to app X?" Which log answers it?
   **A:** **Audit logs** (Enterprise applications filtered view) — consent events record category/activity/status/target/initiator.

### Real-world use cases

- **Law firm, partner-data protection:** Partners review client files from home and airport Wi-Fi. Enabled Application Proxy for the on-prem document system (header-based auth), layered a Conditional Access session policy forcing frequent reauthentication on unmanaged devices — because token lifetimes alone couldn't distinguish a shared laptop from a partner laptop.
- **Healthcare network, joiner-mover-leaver automation:** New nurses waited days for Epic-adjacent SaaS accounts. Turned on automatic provisioning to Workday-connected gallery apps with attribute mappings synced from HR, enabling same-day access and **automatic deprovisioning** on termination — eliminating orphaned accounts holding PHI.
- **Global manufacturer, consent hygiene:** Security feared malicious OAuth apps. Kept user consent but restricted it to **verified publishers + tenant apps with classified low-impact permissions**, relied on default-on **step-up consent** for risky requests, and reviewed audit-log consent events monthly — balancing productivity against illicit-consent phishing.
- **Retail chain, My Apps adoption:** Store managers couldn't find their six workforce apps among hundreds. Created admin-managed **collections** (P1 license) grouped by role in App launchers, so each manager sees a focused tab — cutting password-reset tickets and "where's my app?" calls.

## Unit 3.3 — Implement app registration

### Flashcards

- **Q:** What is an application object, where does it live, and what does it contain? **A:** The **definition/blueprint** of the app telling Entra how to issue tokens — managed in the **App registrations** experience and existing **only in its home directory**, even for multitenant apps. Contents: name/logo/publisher, **redirect URIs**, credentials (**certificates/secrets**), API dependencies (OAuth), published scopes/APIs, **app roles (RBAC)**, SSO/provisioning/proxy metadata & config.
- **Q:** Why integrate applications with Microsoft Entra ID? **A:** For application/user authentication & authorization, **SSO (federation or password)**, user provisioning/sync, **role-based access control via app roles**, OAuth authorization services for M365/APIs, **application publishing/proxy**, and **directory schema extension attributes**. Note: registration establishes a **unidirectional trust** — your app trusts the Microsoft identity platform, never the reverse.
- **Q:** What is a service principal and what does its record hold? **A:** The **instance** of the application in your directory, governed via the **Enterprise applications** experience — one app has at most **one application object** (home tenant) referenced by **one or more SPs**, one per directory where it operates. The record holds: application-ID reference to the app object, **local user/group app-role assignments**, **local consent grants**, **local policies including Conditional Access**, alternate local settings, **claims transformation rules**, **provisioning attribute mappings**, directory-specific app roles/name/logo.
- **Q:** How do service principals come into existence? **A:** First-user **consent during sign-in** to a third-party app; subscribing to **Microsoft 365** (SharePoint even creates them ongoing); admin adds a **gallery app** (creates the app object too); adding an app for **Application Proxy**; connecting an app for **SAML/password SSO**; or programmatically via **Microsoft Graph/PowerShell**.
- **Q:** What are the documented exceptions around service principals? **A:** Not all SPs point back to an app object (legacy PowerShell-created SPs resemble classic AD service accounts); the **Microsoft Graph API requires an application object before creating a service principal**; **claims transformation rules and attribute mappings are configurable only in the UI**, not exposed programmatically.
- **Q:** Which two tenant switches curb default user power over apps, and what happens afterward? **A:** **Users can register applications = No** (Microsoft Entra User settings) and **Users can consent to apps accessing company data on their behalf = No** (Enterprise applications User settings). Afterward an **administrator must consent** to every new app a user needs.
- **Q:** Match the supported-account-types audience options to who can sign in, and what are the multitenant best practices? **A:** **Accounts in this directory only** → single-tenant (internal users/guests). **Accounts in any Microsoft Entra directory** → multitenant work/school (business/education customers). **Any Entra directory + personal Microsoft accounts** → widest reach (adds Skype/Xbox/Outlook.com; social like Google/LinkedIn configurable). Multitenant best practices: **test in a tenant with Conditional Access configured**, request **least privilege**, and write clear permission names/descriptions.
- **Q:** In which direction does the trust relationship run at registration? **A:** **Unidirectional — your app trusts the Microsoft identity platform**, not the other way around.
- **Q:** Which platform tiles exist when configuring authentication, and which generate redirect URIs automatically? **A:** **Web** and **Single-page application** (manual redirect URI); **iOS/macOS** (Bundle ID from Xcode Info.plist), **Android** (Package name + signature hash) generate URIs automatically; **Mobile and desktop** offers suggested/custom URIs (e.g., `https://login.microsoftonline.com/common/oauth2/nativeclient`).
- **Q:** Compare certificate and client-secret credentials. **A:** Both authenticate **confidential clients** (web apps, web APIs, daemon/service apps) without user interaction. **Certificates** (public keys; `.cer`, `.pem`, `.crt`) are **recommended** — higher assurance; **client secrets** (application passwords) are easier, common in dev, less secure for production. The secret **value is displayed only once** — copy it immediately.
- **Q:** What's special about registering a web API, and how do you create a scope on it? **A:** Skip redirect URI/platform config (no interactive sign-in) and skip credentials **unless the API calls a downstream API**. Then: App registration → **Expose an API** → set the globally unique **Application ID URI** (`api://…` default or e.g. `https://contoso.com/api`) → **Add a scope** named by convention `resource.operation.constraint` (e.g., `Employees.Read.All`, admin-and-user-consentable; `Employees.Write.All`, **Admins only**) → optionally **pre-authorize trusted client applications (PCAs)** so their users skip consent. Full scope string = **App ID URI + scope name**.
- **Q:** Contrast delegated and application permissions, including effective permissions. **A:** **Delegated** = app acts as the **signed-in user**; effective permission is the **least-privileged intersection** of granted permission and the user's own privileges — the app can never exceed the user. **Application** = app runs with **no signed-in user** (background services/daemons); effective permission is the **full privilege** of the permission, and **only administrators can consent**. Example: delegated `User.ReadWrite.All` + ordinary signed-in user ⇒ update own profile only; application `User.ReadWrite.All` ⇒ update every profile.
- **Q:** Which four OpenID Connect scopes live on Microsoft Graph, and which OIDC scopes are unsupported? **A:** **openid** (sign-in, `sub` claim, UserInfo endpoint), **email** (email claim only if present), **profile** (given name, surname, preferred username, oid, more), **offline_access** (**refresh tokens** — explicit on v2.0 endpoint; SPAs always receive refresh tokens). **Address and phone are not supported.** Initial consent automatically includes **offline_access and user.read**; access tokens expire quickly (~1 hour).
- **Q:** How do you grant tenant-wide admin consent, what are the caveats, and which permissions are admin-restricted? **A:** From **App registrations > API permissions > Grant admin consent** (requires e.g. **Privileged Role Administrator** or a custom role with consent permission), or **Enterprise applications > Permissions > Grant admin consent**; URL pattern `https://login.microsoftonline.com/{tenant-id}/adminconsent?client_id={client-id}`. Caveats: granting gives the app/publisher access to org data, and via App registrations it **revokes previously granted tenant-wide consents** (user-level grants unaffected). Admin-restricted examples: **User.Read.All, Directory.ReadWrite.All, Groups.Read.All** — org users can't consent to these; **application permissions can only be requested via the admin consent endpoint** (`/v2.0/adminconsent`; scope may be `/.default`; don't use `common` since personal accounts can't provide admin consent).
- **Q:** How are app roles defined, emitted, and assigned? **A:** Declared via the **App roles UI (public preview)** or **manifest editor** (Allowed member types: Users/Groups/Applications; Value like `Survey.Create`; **description mandatory**). At sign-in Entra emits a **roles claim** covering individually assigned roles plus group-derived ones. Assignment happens on the **enterprise app** under **Users and groups**, picking a role in the assignment dialog.
- **Q:** What is the app governance add-on? **A:** A **Defender for Cloud Apps add-on** providing insight/governance/detection/remediation for **OAuth-enabled apps accessing Microsoft 365 data via Microsoft Graph** — dashboards, proactive/reactive policies, anomaly alerts, and automatic remediation; verify integration via the Microsoft 365 OAuth app Reputation / Phishing Detection / App Governance policies appearing in MDCA.

### Understand-check questions

1. Your multitenant ISV app works everywhere except a customer tenant with strict CA policies. Per best practice, what should have caught this?
   **A:** Testing the app in a tenant with Conditional Access policies configured before release.
2. Client app got `User.ReadWrite.All` delegated consent, yet can only edit the signed-in user's profile. Why?
   **A:** Effective delegated permission = intersection with the user's privileges; a non-admin user caps the app at the user's own data.
3. Why does a daemon app fail with a normal /authorize request for application permissions?
   **A:** Application permissions must go through the **admin consent endpoint**; there is no signed-in user to consent.
4. After clicking Grant admin consent in App registrations, some departments lost app functionality. What happened?
   **A:** That action **revokes previously granted tenant-wide admin consents**; re-review and re-grant (user-level consents were untouched).
5. You must let a trusted internal client call your API without ever prompting employees. Two mechanisms?
   **A:** Pre-authorize the client (PCA) under Expose an API, and/or have an admin grant tenant-wide consent.
6. Where in code should a web API enforce fine-grained access, and what claim drives it?
   **A:** Evaluate the **scope (`scp`) claim(s)** of the incoming OAuth 2.0 access token — the API controls access at runtime from those claims.

### Real-world use cases

- **SaaS startup, publishing an API:** Shipped an employee-data API consumed by customer HR portals. Registered the API, set App ID URI `https://contoso.com/api`, exposed `Employees.Read.All` (users+admins) and `Employees.Write.All` (**Admins only**), and pre-authorized its own flagship client — customers onboard without bespoke permission wiring, honoring least privilege.
- **Bank, nightly reconciliation daemon:** A background job must read every user's mailbox at 2 AM with nobody signed in. Registered a confidential-client app with a **certificate** (not a secret), requested **application permission** Mail.Read, and had a Privileged Role Administrator grant consent via the **admin consent endpoint** — because delegated flows are impossible without an interactive user.
- **Hospital chain, runaway OAuth apps:** Clinicians kept approving sketchy calendar apps. Deployed the **app governance add-on to Defender for Cloud Apps** for Graph-accessing OAuth apps: anomaly detection flagged an app requesting Mail.Send from 200 users within days and auto-remediated by disabling it — turning consent from a silent risk into a monitored pipeline.
- **University, developer autonomy with guardrails:** CS students needed to register capstone project apps. Left registration on but taught the blueprint model: each student becomes **first owner** automatically, owns lifecycle, and loses access automatically at graduation — visibility and audit trails replaced the old AD FS admin-ticket process.

## Unit 3.4 — Register apps using Microsoft Entra ID

### Flashcards

- **Q:** What does registering an app give you, at a high level? **A:** An identity configuration integrating with the Microsoft identity platform: **custom branding** in the sign-in dialog, **tenant configuration** (single/multitenant, personal Microsoft accounts, social like Google/LinkedIn), **permission management** (request scopes like `user.read`; define scopes for your own web API), and **secure authentication** (secrets, certificates, or managed identities for confidential clients).
- **Q:** Define a confidential client application. **A:** An app that can **hold credentials securely** — e.g., a web app with a trusted back-end server storing the credential; contrast with public clients (SPA/mobile) that can't safely keep secrets.
- **Q:** When are service principals created for single-tenant vs multitenant apps? **A:** Single-tenant: **one SP in the home tenant**, created at registration. Multitenant: SP at registration in the home tenant **plus one SP in every other tenant, created during the first user authentication** (consent) there.
- **Q:** What changed about access-token versions for new applications in August 2024? **A:** New applications receive **v2 access tokens by default** (instead of v1) for improved security — affecting token format and contained claims.
- **Q:** What identifiers/values must you record right after registration? **A:** The **Application (client) ID** and **Directory (tenant) ID** from the Overview page — both are needed to configure application code.
- **Q:** Explain the application-object-as-template analogy and what the object contains. **A:** Like a **class in OOP**: static properties applied to every created instance (service principal). It describes **how tokens are issued** to the app, **what resources it might access**, and **what actions it can take**. Contents: name/logo/publisher, **redirect URIs**, credentials (**certificates recommended**; secrets only when certificates aren't feasible), API dependencies, published scopes, **app roles**, SSO/provisioning/proxy metadata & config.
- **Q:** Name the three types of service principals. **A:** **Application** (local instance of a global app object), **Managed identity** (recommended for **Azure workloads** — eliminates developer credential management), **Legacy** (apps predating app registrations; migrate to modern registrations when possible).
- **Q:** State the cardinality relationships of an application object. **A:** **One-to-one** with the software application; **one-to-many** with its service principals — an SP must exist in **each tenant** where the app is used.
- **Q:** What happens when you modify or delete an application object? **A:** Changes/deletions affect the SP **in the home tenant** (deleting the app object deletes the home-tenant SP). **Restoring the application object does NOT restore its service principal.** SPs in other tenants remain **independent** of the home tenant's app object.
- **Q:** How do you locate the service principal tied to a registration? **A:** In the app registration's Overview, select **Managed application in local directory**.
- **Q:** List the core steps to create an app registration. **A:** Entra admin center (minimum **Application Developer** role) → Identity > Applications > **App registrations** > **New registration** → enter Name → choose **Supported account types** → per current guidance, **do NOT enter a redirect URI at this stage** → Register → record client ID + tenant ID.
- **Q:** Why configure an SPA through the Single-page application tile rather than Web? **A:** The SPA platform enables the **authorization code flow with PKCE plus CORS** (MSAL.js 2.0+) — more secure than the legacy **implicit grant flow**; leave both Implicit grant/hybrid-flow checkboxes **unchecked**.
- **Q:** Are new app registrations visible to users by default? **A:** No — **hidden by default**. Enable via **Enterprise apps > Properties > Visible to users? = Yes** to surface the app in My Apps.
- **Q:** Recite the redirect URI constraints. **A:** Must start with **https** (**localhost exception** for development); **case-sensitive** match against the running app's URL path; URIs **without a path segment** are returned **with a trailing slash**, those **with a path segment** get **no appended slash**; special characters **! $ ' ( ) , ;** are not supported.
- **Q:** Why prefer app roles over group claims for app authorization? **A:** Avoids **group overage** issues, **doesn't require Microsoft Entra ID P1** licensing (unlike group claims in tokens), yields fine-grained authorization, and simplifies code — check for `"admin"` in the **roles** claim instead of mapping group GUIDs. Tokens carry roles in **ID tokens (apps)** and **access tokens (APIs)**, e.g., `"roles": ["Approver","Reviewer"]`.
- **Q:** What is the golden rule when defining user-assignable app roles with assignment-required apps? **A:** Always define a **baseline user role** (no elevated rights). Since every user/group assignment **must include one of the defined roles**, omitting a base role would force everyone onto the highest role (e.g., admin) — violating least privilege.

### Understand-check questions

1. A customer reports your multitenant app missing from their tenant's Enterprise apps until someone signs in. Expected?
   **A:** Yes — the SP materializes in a consuming tenant **at first user authentication/consent**, not at publisher registration time.
2. You deleted an app registration by mistake and restored it from the admin center. Sign-ins still fail. Why?
   **A:** Restoring the application object **does not restore the home-tenant service principal**; recreate/repair the SP.
3. Which credential should an Azure-hosted web API use to call Key Vault, and why?
   **A:** A **managed identity** — the preferred approach for Azure workloads; no secret to rotate, no credential management at all.
4. Your React SPA still requests tokens via implicit flow. What's the modern correction?
   **A:** Reconfigure the platform as **Single-page application** and use **authorization code flow with PKCE**; clear implicit-grant checkboxes.
5. Why did a token arrive for `https://contoso.com/users` when the app requested `https://contoso.com/Users`?
   **A:** Redirect URIs are **case-sensitive** and must exactly match the registered casing.
6. Product wants every new hire auto-assigned "Reader," only leads "Approver." How do you encode this?
   **A:** Define app roles **Reader** (baseline) and **Approver**, set **User assignment required**, assign groups to each role — roles arrive in the token's **roles** claim.

### Real-world use cases

- **Fintech scale-up, credential rotation pain:** Their production daemon used client secrets that expired quarterly, causing 2 AM outages. Moved Azure-hosted components to **managed identities** and remaining VMs to **certificate credentials** — because certificates give higher assurance than passwords and managed identities remove credential management entirely.
- **HR-tech ISV, multitenant onboarding:** Customers complained the app appeared broken post-install. Root cause: SPs only appear in a tenant **after first consent**, plus branding mismatch at sign-in. Fixed by documenting the consent-first flow, custom-branding the sign-in dialog, and testing against a CA-hardened trial tenant before each release.
- **Logistics firm, least-privilege rollout:** Warehouse portal originally granted every worker supervisor rights because no baseline role existed when user assignment became required. Redefined app roles with a **Reader** baseline plus **Dispatcher/Supervisor** tiers and mapped AD groups — enforcing least privilege directly from the roles claim with zero code mapping of group GUIDs.
- **Agency, SPA modernization:** A legacy AngularJS app relied on implicit-flow ID tokens flagged in a pen test. Re-registered with the **SPA platform (PKCE + CORS)**, updated to MSAL.js 2.x, validated localhost dev redirect handling, and confirmed no trailing-slash mismatch in production — closing a token-leak vector.

## Exam traps

1. **Application object vs service principal:** App object = **blueprint**, lives **only in the home tenant**, managed under *App registrations*; SP = **instance**, one per tenant where used, managed under *Enterprise applications*. Deleting the app object removes the home-tenant SP, but **restoring the app object does NOT restore the SP**; foreign-tenant SPs stay independent. Not every SP points back to an app object (legacy), but **Graph requires the app object first**.
2. **scp vs roles claim split:** Fine-grained **API/data access** is enforced from the **`scp` (scope) claim** in the OAuth access token (delegated vs application permissions); **in-app user authorization** comes from the **`roles` claim** populated by assigned **app roles**. Mixing them up — checking `roles` for API scopes or `scp` for app screens — is the classic wrong-answer bait.
3. **Secret expiry risk:** Client secrets are passwords with a maximum validity window and a **shown-once value**; forgetting rotation causes outages. Certificates are **recommended**; **managed identities eliminate credential management** for Azure workloads (system-assigned tied to the resource lifecycle, user-assigned standalone).
4. **Delegated ≠ application effective permissions:** Delegated = intersection with signed-in user's privileges (**never exceeds the user**); application = full privilege, **admin-only consent**, no user context. Questions love `*.Read/ReadWrite.All` scenarios flipping these two.
5. **Role-boundary gotchas:** **Cloud Application Administrator = Application Administrator minus application proxy**; neither manages **Conditional Access**, neither is auto-added as owner. Owners: **groups can never own** anything; **service principals can own app registrations but only users own enterprise applications**; owners/admins can add credentials and **impersonate the app** (privilege elevation).
6. **Consent mechanics:** Risk-based **step-up consent is on by default** (only bites when end-user consent is enabled); tenant-wide admin consent granted via *App registrations* **revokes prior tenant-wide grants**; **application permissions require the admin consent endpoint**; `common` can't be used for admin consent (personal accounts can't consent for a tenant).
7. **Feature-license and placement traps:** My Apps **collections require Entra ID P1/P2**; Application Proxy is for **remote/external** users only (connector on-prem; KCD for IWA) and is absent from the Cloud Application Administrator role; **SCIM defines /Users and /Groups endpoints**; AD FS migration report statuses are **Ready to migrate / Needs review / Additional steps required**; SPA platform = **auth-code flow + PKCE**, implicit grant checkboxes stay unchecked.
