Lesson 0001 — Conditional Access Evaluation Logic

Mission link: CA is the single largest mark block on SC-300 (D2, 25–30%). This lesson teaches the evaluation engine — the thing every CA question is secretly testing.

The three laws of policy evaluation

Law 1 — All matching policies evaluate. There is no "first match wins." Every policy whose assignments (users, cloud apps, conditions) match the sign-in applies. Ten policies can apply at once.
Law 2 — Grant controls accumulate (AND across policies). If Policy A requires MFA and Policy B requires a compliant device, the user needs both. Across policies, requirements always stack to the most restrictive combination.
Law 3 — Block always wins. Any applicable policy with a Block control denies access unconditionally. No other policy can rescue the sign-in. There is no voting.

Applying the laws to legacy authentication

What "legacy auth" means: protocols that predate modern auth (OAuth 2.0 / OIDC token exchange) — IMAP, POP3, SMTP AUTH, and old Office clients. They only know username + password.

The mechanism that matters: legacy clients have no UI and no token flow for a second factor. They cannot satisfy MFA even in principle. So:

Policies applying to an IMAP sign-inOutcome
Block legacy authDenied — Law 3
Require MFA onlyDenied anyway — IMAP cannot perform MFA
BothDenied — Block wins; MFA was moot

This is why Microsoft's #1 baseline recommendation is "Block legacy authentication": it's simultaneously a security control (credential-stuffing favorite, phishable, invisible to Conditional Access richness) and an enabler (forces modern auth, which supports MFA, CAE, device compliance).

The universal decision tree (use on EVERY CA question)

  1. Which policies match? Check assignments: users/groups/roles, cloud apps, network locations, device state, client app type.
  2. Any Block? → Denied. Stop.
  3. Collect grant controls from ALL matching policies → they AND together.
  4. Within a single policy: multiple selected controls default to AND — OR requires explicitly choosing "Require one of the selected controls."
  5. Session controls (sign-in frequency, app-enforced restrictions) apply after access is granted.

The traps (this is what the exam actually tests)

Trap 1 — The AND/OR inversion. Distractors claim multiple controls within one policy mean OR by default. False. Default is AND ("Require all").
Trap 2 — Exclusion scope. An exclusion removes the user from THAT policy only — other policies still apply to them. Break-glass accounts must be excluded from every policy.
Trap 3 — Report-only ≠ enforce. Report-only evaluates and logs in sign-in logs' CA tab but never blocks. What-If simulates without any sign-in at all.
Trap 4 — "Which policy decides?" Wrong frame — there is no deciding policy. ALL evaluate; the COMBINATION decides.

Retrieval practice — answer cold, then check

R1. Policy A requires MFA for Exchange. Policy B blocks legacy auth. IMAP sign-in with username+password. What happens?

Show answerBlocked by B (Law 3). A is irrelevant — legacy auth couldn't satisfy MFA regardless.

R2. Same two policies, but the user uses modern Outlook on an unmanaged laptop. Policy C separately requires compliant device for Exchange. Outcome?

Show answerMFA prompted (A). After satisfying it, still denied — C's compliant-device requirement stacks via Law 2. Unmanaged device fails it.

R3. One policy selects "Require MFA" + "Require approved app" and leaves the default multi-control setting. What must a user satisfy?

Show answerBoth — default within one policy is "Require ALL selected controls" (AND). OR needed explicit selection.

R4. A Global Admin is excluded from the block-legacy-auth policy. She signs in via IMAP. Any other policies apply? What happens?

Show answerExclusion removed her from B only. If any other policy matches her + IMAP (e.g., an MFA requirement), it still applies — and legacy auth can't do MFA, so denial. If nothing else matches, the sign-in succeeds — which is exactly why break-glass exclusions are dangerous without compensating monitoring.
