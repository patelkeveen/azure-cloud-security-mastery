## D1 — Implement and manage user identities · 20-25%

*Revision budget: About 300 minutes total for D1, spread Mon-Wed with a 30-minute Thursday recall pass.*

### Discriminators

**Administrative unit (AU)** vs **Custom Entra role**
- An AU constrains WHICH objects (users/groups/devices) a role assignment reaches; a custom role constrains WHAT actions (permissions) the assignee has. AUs cannot be nested; an object can be in several AUs. Custom roles need P1 per assignee; AU-scoped admins need P1, AU members only Free.
- **Tell:** 'only for users in the Germany office / School of Business' = AU + built-in role. 'can only update credentials/basic properties, nothing else' = custom role. 'both limits at once' = custom role assigned at AU scope.

**Restricted management administrative unit** vs **Regular administrative unit**
- In a restricted management AU only admins explicitly assigned at THAT AU's scope can modify member objects; tenant-scoped Global Administrator, Privileged Role Administrator, User Administrator etc. are blocked from editing members (GA/PRA can still manage the AU itself and assign themselves). Must be set at creation, immutable, max 100 per tenant, M365 groups not allowed, members lose PIM/entitlement/access-review/lifecycle-workflow governance. A regular AU adds scope for the AU admin but does not remove tenant-wide admins' rights.
- **Tell:** 'protect executive / break-glass accounts from Helpdesk Administrators or a compromised tenant-level admin' = restricted management AU. 'delegate regional helpdesk' = regular AU.

**Role-assignable group (isAssignableToRole = true)** vs **Ordinary security / M365 group**
- Role-assignable: property set only at creation and immutable, membership must be Assigned (never dynamic), creator needs at least Privileged Role Administrator, max 500 per tenant, no nesting, needs P1, members' credentials/MFA can only be changed by Privileged Authentication Administrator. Ordinary groups can be dynamic and nested but cannot receive Entra roles.
- **Tell:** 'assign the Helpdesk Administrator role to a group' = must be role-assignable created fresh. Any option that converts an existing group or uses a dynamic rule for a role is wrong by design.

**Dynamic membership** vs **Assigned membership**
- Dynamic: rule-driven (user.department -eq "Sales"), P1 per unique user member (devices free), max 15,000 dynamic groups per tenant, rule body max 3,072 chars, cannot mix user.* and device.* in one rule, members cannot be added manually. Assigned: manual, required for role-assignable groups and for staged-rollout groups (nested and dynamic groups are NOT supported there).
- **Tell:** 'automatically based on attribute' = dynamic. 'group for a directory role' or 'group for staged rollout' = assigned only.

**Security group** vs **Microsoft 365 group**
- Security group = permission list, can contain users OR devices, no mailbox. M365 group = collaboration (mailbox, SharePoint site, Teams), users only, is the ONLY group type the expiration policy applies to (P1; 30/15/1-day owner notices; restore within 30 days).
- **Tell:** 'shared mailbox / Teams / SharePoint site created automatically' or 'group expiration policy' = M365 group. 'device-based dynamic group' = security group.

**Password hash synchronization (PHS)** vs **Pass-through authentication (PTA)**
- PHS: hash-of-hash synced every 2 minutes, auth happens in Entra, survives on-prem outage, required for Identity Protection leaked-credential detection regardless of primary method, but enforces on-prem account states with up to 30-min delay (disabled) and does not enforce sign-in hours/lockout/expired password. PTA: lightweight agents validate against DCs at sign-in, enforces on-prem states (disabled, locked, expired, sign-in hours) immediately, three agents recommended, max 12 per tenant, dies with on-prem; failover to PHS is NOT automatic - must switch sign-in method in Connect.
- **Tell:** 'must keep working if datacentre is down / ransomware' or 'leaked credentials report' = PHS. 'password must never leave premises' or 'enforce sign-in hours / immediate account disable' = PTA (with PHS as backup).

**Cloud authentication (PHS/PTA)** vs **Federation (AD FS)**
- Federation hands sign-in to an external STS: needed for third-party MFA providers, smart card/certificate via AD FS, sAMAccountName (DOMAIN\user) sign-in, third-party auth systems; costs 2+ AD FS + 2+ WAP servers, TLS certs, Connect Health for monitoring. Cloud auth needs none of that. Microsoft recommends PHS and enabling PHS even alongside federation as backup.
- **Tell:** 'third-party MFA', 'existing AD FS investment must be kept', 'DOMAIN\username sign-in' = federation. Otherwise cloud auth; 'lowest cost/complexity' = PHS.

**Microsoft Entra Connect Sync** vs **Microsoft Entra Cloud Sync**
- Cloud Sync: lightweight provisioning agent, cloud-managed config, multiple active agents, DISCONNECTED forests supported, group provisioning to AD, on-demand provisioning; limits 150K objects/domain and 50K group members; NO device sync (hybrid join), NO PTA/AD FS configuration, no advanced sync rules, no cross-forest references or attribute merge. Connect Sync: single on-prem engine (staging server for HA), device writeback/hybrid join, PTA and federation config, advanced rules, unlimited scale. Both do PHS, password writeback, Exchange hybrid attributes, group writeback v1, seamless SSO.
- **Tell:** 'merged companies, forests do not trust each other' or 'no single point of failure' = Cloud Sync. 'hybrid Entra join / device sync', 'configure PTA', 'complex sync rules', '>150K objects' = Connect Sync.

**Seamless SSO (Kerberos, AZUREADSSO computer account)** vs **SSO via Primary Refresh Token (PRT)**
- Seamless SSO: for domain-joined Windows 7/8.1 (and non-Entra-joined devices) on the corporate network, works with PHS and PTA only (NOT AD FS), free, opportunistic, roll the Kerberos decryption key at least every 30 days. PRT-based SSO: Windows 10/11 Entra joined, hybrid joined or registered devices; the recommended path.
- **Tell:** 'domain-joined devices, no additional infrastructure, Windows 7/8.1' = seamless SSO. 'Windows 10/11 Entra joined' = PRT. Any 'seamless SSO with AD FS' option is wrong.

**Staged rollout** vs **Domain cutover (convert federated domain to managed)**
- Staged rollout moves selected groups of users (cloud-only assigned groups; nested/dynamic not supported) from federation to PHS/PTA/seamless SSO WITHOUT changing the domain's federation setting - a test/migration ramp requiring Hybrid Identity Administrator. Cutover = Update-MgDomain -DomainId contoso.com -AuthenticationType Managed (Graph PowerShell), can take up to 60 minutes, whole domain at once; turn staged rollout off afterwards.
- **Tell:** 'pilot / test a subset of users before migrating from AD FS' = staged rollout. 'decommission AD FS / finish migration' = convert domains to managed then remove relying party trust.

**B2B collaboration** vs **B2B direct connect**
- Collaboration: invitation + redemption creates a Guest user object (UPN email_domain#EXT#@tenant.onmicrosoft.com) in your directory; enabled by default with all Entra orgs; works for M365, SaaS, custom apps, entitlement management. Direct connect: mutual two-way trust configured in cross-tenant access settings by BOTH tenants, NO user object created, currently only Teams shared channels, blocked by default, needs P1 in both tenants, and if your CA requires MFA you MUST trust MFA claims inbound.
- **Tell:** 'must not appear in our directory' / 'Teams shared channel' = direct connect. 'access SharePoint site / enterprise app / access package' = collaboration.

**Cross-tenant access settings** vs **External collaboration settings**
- Cross-tenant access settings (Security Administrator to configure; P1 for trust settings): per-organization inbound/outbound rules for OTHER MICROSOFT ENTRA tenants - B2B collaboration, direct connect, trust MFA/compliant/hybrid-joined claims, automatic redemption, cross-tenant sync allow-list, redemption order. External collaboration settings (Global Admin or External Identity Provider Administrator): tenant-wide guest user access level (same as members / limited [default] / restricted), who can invite (4 levels + Guest Inviter role), allow/deny domain list, self-service sign-up, external user leave settings.
- **Tell:** 'partner tenant Fabrikam', 'trust MFA from their tenant', 'guests asked to register MFA twice' = cross-tenant access settings. 'block gmail.com invitations', 'guests cannot enumerate directory', 'only admins may invite' = external collaboration settings.

**Inbound settings (resource tenant)** vs **Outbound settings (home tenant)**
- Inbound controls what EXTERNAL users may reach in YOUR tenant and holds the trust settings your CA honours. Outbound controls what YOUR users may reach in external tenants. Automatic redemption suppresses the consent prompt only when BOTH home-tenant outbound AND resource-tenant inbound have it checked; direct connect needs both sides mutually enabled.
- **Tell:** 'our users cannot access Fabrikam's app' = your outbound (or Fabrikam's inbound). 'Fabrikam guests blocked from our app' = your inbound. 'consent prompt still appears' = the other side's checkbox is missing.

**Cross-tenant synchronization** vs **Manual / bulk B2B invitation (or entitlement management)**
- Cross-tenant sync: automated push provisioning from source tenant into target tenant creating/updating/soft-deleting B2B users (default userType member) and security groups, fixed 40-minute cycle, target enables 'Allow user synchronization into this tenant' inbound + automatic redemption, P1 per synced user in SOURCE tenant, intended for multitenant organizations not cross-company. Invitation: one-off, creates guest pending acceptance, sends email, no lifecycle. Entitlement management: request/approval-driven guest creation with expiry, for cross-organization partners.
- **Tell:** 'organization owns multiple tenants / lifecycle automatically removed when user leaves' = cross-tenant sync. 'partner company staff request access with approval and expiry' = entitlement management + connected org. 'invite 200 contractors from CSV' = Users > Bulk operations > Bulk invite.

**Microsoft Entra registered** vs **Microsoft Entra joined / hybrid joined**
- Registered = BYOD/personal (Windows personal, iOS, Android, macOS) via 'add work account', governed by 'Users may register their devices' (forced to All if Intune/MDM configured). Joined = organization-owned Windows 10/11, macOS, Linux, sign in with work account, governed by 'Users may join devices' (default All). Hybrid joined = on-prem AD-joined AND registered via Connect Sync (not Cloud Sync); the 'max devices per user' (default 50, up to 100 or Unlimited) and 'require MFA to register/join' toggles do NOT apply to hybrid join. Cloud Device Administrator is the least-privileged role to change device settings.
- **Tell:** 'personal phones' = registered. 'corporate laptops, cloud-only' = joined. 'existing domain-joined PCs with Group Policy' = hybrid joined (needs Connect Sync).

**Authentication Administrator** vs **Privileged Authentication Administrator vs Authentication Policy Administrator**
- Authentication Administrator: view/set/reset auth methods (MFA) and passwords for NON-admin users, can be AU-scoped. Privileged Authentication Administrator: same for ANY user including Global Admins and members of role-assignable groups; also 'reset password of privileged admins'. Authentication Policy Administrator: the tenant-wide authentication methods policy (enable/disable methods, TAP policy, delete app passwords) - not per-user resets.
- **Tell:** 'policy / enable passkeys tenant-wide' = Authentication Policy Admin. 'reset MFA for a user' = Authentication Admin. 'including administrators / a Global Administrator's MFA' = Privileged Authentication Admin.

**Password Administrator / Helpdesk Administrator** vs **User Administrator**
- Password Administrator: least-privileged role to reset passwords of non-admins (AU-scopable). Helpdesk Administrator: reset non-admin passwords + invalidate refresh tokens + reset guest invites + read BitLocker keys. User Administrator: create/delete/restore users, bulk create, assign licenses, create groups, reset passwords of limited admins, manage group expiration. Reset password of privileged admins = Privileged Authentication Administrator. License-only work = License Administrator; group-only = Groups Administrator; guest-invite-only = Guest Inviter.
- **Tell:** 'least privileged role to reset passwords' = Password Administrator. 'create users / bulk create / restore deleted users' = User Administrator. 'assign licenses only' = License Administrator.

**Custom security attributes** vs **Extension attributes (extensionAttribute1-15 / directory extensions)**
- Custom security attributes: key-value pairs in attribute sets, assignable to users and service principals only, read/write gated by dedicated roles (Attribute Definition Administrator, Attribute Assignment Administrator, Attribute Assignment Reader/Log Reader) - Global Administrator has NO access by default; used for Azure ABAC and app filtering; NOT emitted in SAML/JWT claims; free; 500 definitions/tenant. Extension attributes: readable by anyone who can read the object, can be synced from AD, usable in dynamic group rules and claims.
- **Tell:** 'sensitive data such as hourly salary, restrict who can read it, authorization / ABAC' = custom security attributes; then 'which role' = Attribute Definition/Assignment Administrator, never Global Administrator. 'dynamic group rule on extensionAttribute15' = extension attribute.

**Microsoft Entra roles (directory)** vs **Azure RBAC roles (resources)**
- Entra roles govern directory objects via Microsoft Graph and are tenant/AU/resource-scoped; Azure roles (Owner, Contributor, User Access Administrator) govern Azure resources via ARM at management group/subscription/RG/resource scope. A Global Administrator has NO Azure resource access until they flip 'Access management for Azure resources' in Entra ID > Properties, which grants User Access Administrator at root scope '/' - per-user, audited, remove afterwards.
- **Tell:** 'Global Administrator cannot see subscriptions / lost access to a subscription' = elevate access. 'Entra role permissions cannot be added to an Azure custom role' = the two systems are separate.

**userType (Member vs Guest)** vs **Identities / source (ExternalAzureAD, Microsoft account, mail OTP, {issuer URI})**
- userType expresses relationship to the org and drives default permissions and policies; it is independent of how the user authenticates. Identities shows the IdP: ExternalAzureAD (other Entra tenant), Microsoft account, mail (email one-time passcode, on by default for new tenants), google.com/facebook.com, or a SAML/WS-Fed issuer URI. B2B users can be invited as external MEMBERS (multitenant orgs) and userType can be converted in the portal.
- **Tell:** 'guest cannot enumerate users' = userType Guest + guest access restriction. 'user authenticates with their own AD FS at partner' = SAML/WS-Fed federation shows as issuer URI. 'Invitation state: Pending acceptance' = not yet redeemed (externalUserState).

**Soft-deleted user (restorable)** vs **Permanently deleted user**
- Deleted users sit in Deleted users for 30 days and can be restored with all properties and their licenses (even if that puts you over the license count); after 30 days permanent deletion starts automatically and cannot be stopped; 'Delete permanently' is irreversible even for Microsoft support. A synced user deleted in Entra can be re-created by the next sync cycle if it still exists on-prem.
- **Tell:** 'user deleted 20 days ago, need mailbox and group memberships back' = restore from Deleted users (User Administrator). 'deleted 45 days ago' = gone; create new. 'deleted synced user reappeared' = AD is authoritative.

**Group-based (inherited) license** vs **Direct license**
- Group-based: assigned on the group, reconciled to members, nested groups NOT supported (only first-level members), up to 20 groups per assign operation, errors surface on the product's Errors & issues tab (insufficient licenses, conflicting service plans, missing dependencies, proxy address, usage location not allowed); removing the user from the group removes the inherited license; move users by add-to-new-group first, confirm, then remove from old. Direct: per-user, needs usage location set first. Roles: License Administrator (least) / Groups Administrator / User Administrator.
- **Tell:** 'users in nested group did not get the license' = nesting unsupported. 'avoid service interruption when moving between licensed groups' = add first, remove second. 'why does the user still have the license after removal from group' = also directly assigned.

**Usage location** vs **Country/region (address attribute)**
- usageLocation is the two-letter code licensing checks for service availability; country is a profile/address field used in dynamic rules but irrelevant to licensing. For direct assignment usage location must be set; for group-based licensing users without one inherit the tenant's location, and the failure class is 'usage location not allowed' for region-restricted service plans.
- **Tell:** 'license assignment fails for users in a particular country' = set/inspect usageLocation. 'dynamic group of users in India' = user.country or user.usageLocation in the rule.

### High-yield facts

- Administrative units cannot be nested; a user can be a member of several AUs; adding a GROUP to an AU scopes the group object only - an AU-scoped User Administrator cannot reset passwords or manage MFA of that group's members unless the users are added directly; dynamic AU membership exists for users and devices (P1 per member), never groups; AU admins need P1, members only Free.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/administrative-units>
- Restricted management AU: tenant-scoped Global Administrator and Privileged Role Administrator CANNOT modify member objects (only manage the AU and assign themselves); the setting is chosen at creation and cannot be changed; max 100 per tenant; users, devices and security groups only (no M365 groups); members are excluded from PIM, entitlement management, lifecycle workflows and access reviews; assigning licenses and usage location remains allowed.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/admin-units-restricted-management>
- Roles that can be assigned at AU scope include Authentication Administrator, Attribute Assignment Administrator/Reader, Cloud Device Administrator, Groups Administrator, Helpdesk Administrator, License Administrator, Password Administrator, Printer Administrator, Privileged Authentication Administrator, SharePoint Administrator, Teams Administrator, Teams Devices Administrator, User Administrator and any custom role touching users/groups/devices; AU-scoped Helpdesk/Password admins can only act on NON-admin users; role assignment itself requires Privileged Role Administrator.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/manage-roles-portal>
- Role-assignable groups: isAssignableToRole is set only at creation and is immutable; membership type must be Assigned (dynamic forbidden to stop privilege escalation via attribute edits); creating one needs at least Privileged Role Administrator; max 500 per tenant; nesting not supported; changing credentials/MFA of members needs Privileged Authentication Administrator; P1 required (PIM eligibility needs P2); soft-deleted for 30 days.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/groups-concept>
- Dynamic membership: a rule cannot contain both user and device attributes; max 15,000 dynamic groups per tenant; rule body max 3,072 characters; -match is regex, -contains is partial string (both discouraged for performance); -in/-notIn take a bracketed list; 'Direct Reports for "<managerObjectId>"' and 'user.objectId -ne null' (all users) are special rules; the rule builder handles up to five expressions and is user-groups only; P1 needed per unique user member, no license for devices.  
  <https://learn.microsoft.com/en-us/entra/identity/users/groups-dynamic-membership>
- Group-based licensing does not support nested groups (only first-level members get licenses); at most 20 groups can be targeted in one assign operation; users without a usage location inherit the tenant's location for group-based assignment; errors (insufficient licenses, conflicting service plans, missing dependencies, proxy address, usage location not allowed) are shown on the product's Errors & issues tab and fixed with Reprocess; to move users between licensed groups add to the destination group first, confirm, then remove from the source. Least-privileged roles: License Administrator, Groups Administrator or User Administrator.  
  <https://learn.microsoft.com/en-us/entra/fundamentals/concept-group-based-licensing>
- Least-privileged roles by task (verified table): create user = User Administrator; create guest user = Guest Inviter; assign/revoke license = License Administrator; create group = Groups Administrator; reset password of non-admins = Password Administrator; reset password of limited admins = User Administrator; reset password of privileged admins = Privileged Authentication Administrator; manage individual users' authentication methods = Authentication Administrator; configure authentication methods policy = Authentication Policy Administrator; manage domains = Domain Name Administrator; configure company branding = Organizational Branding Administrator; configure guest user access restrictions = Privileged Role Administrator; delete/disable/enable device = Cloud Device Administrator; read audit and sign-in logs = Reports Reader.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/delegate-by-task>
- Custom security attributes: Global Administrator and other admin roles have NO permission to read, define or assign them by default; Attribute Definition Administrator is the minimum to manage definitions/attribute sets and Attribute Assignment Administrator to assign values (both assignable at tenant or attribute-set scope, and the assignment roles at AU scope); supported only on users and service principals; not available in SAML/JWT claims or Entra Domain Services; free in all editions; limits 500 definitions and 500 attribute sets per tenant, 50 values per object.  
  <https://learn.microsoft.com/en-us/entra/fundamentals/custom-security-attributes-overview>
- Bulk create users: Entra ID > Users > Bulk create, at least User Administrator; CSV must keep the 'version:v1.0' first row and header row unchanged; only four columns are required - Name [displayName], User name [userPrincipalName], Initial password [passwordProfile], Block sign in (Yes/No) [accountEnabled]; no invitation emails are sent (internal member accounts); results in Bulk operation results; verify with Get-MgUser -Filter "UserType eq 'Member'". Bulk invite of guests is Users > Bulk operations > Bulk invite with required columns 'Email address to invite' and 'Redirection url'.  
  <https://learn.microsoft.com/en-us/entra/identity/users/users-bulk-add>
- Deleted users remain in a suspended state for 30 days and can be restored with all properties and licenses (even if that exceeds purchased licenses); after 30 days permanent deletion starts automatically and cannot be stopped; 'Delete permanently' cannot be undone by anyone including Microsoft support; Entra is not the source of authority for synced users, so a synced user deleted in Entra may be restored by the next sync cycle.  
  <https://learn.microsoft.com/en-us/entra/fundamentals/users-restore>
- PHS runs every two minutes as part of Connect Sync; Microsoft Entra ID Protection needs PHS regardless of sign-in method for the leaked-credentials report (only leaks found after PHS is enabled are matched); PHS enforces disabled accounts with up to a 30-minute delay and does not enforce lockout/expired/sign-in hours; PTA does enforce all of those; PTA: three agents recommended, up to 12 per tenant, agents need outbound internet and DC access (not in a DMZ); failover from PTA/federation to PHS is manual via Connect; deploy PHS alongside PTA/federation as a backup.  
  <https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/choose-ad-authn>
- Cloud Sync vs Connect Sync comparison table: Cloud Sync uniquely supports disconnected forests, multiple active agents, group provisioning to AD, on-demand provisioning and cloud-managed configuration; it does NOT support device synchronization (hybrid Entra join), PTA/AD FS configuration, advanced sync rules, cross-forest references, attribute merge from multiple domains or reconciliation; limits 150,000 objects per domain and 50,000 members per group (Connect: unlimited / 250K). Both support PHS, password writeback, Exchange hybrid attributes, directory extensions, OU filtering, group writeback v1 and seamless SSO. Device writeback is discontinued in favour of Cloud Kerberos Trust.  
  <https://learn.microsoft.com/en-us/entra/identity/hybrid/cloud-sync/connect-to-cloud-sync-decision-guide>
- Seamless SSO works with PHS and PTA only and is NOT applicable to AD FS; it is free; it requires domain-joined devices and is not used on Windows 10/11 Entra joined or hybrid joined devices (they use the PRT); the AZUREADSSO computer account's Kerberos decryption key should be rolled at least every 30 days; staged rollout needs Hybrid Identity Administrator, cloud-only assigned groups (nested and dynamic groups unsupported), and domain conversion to managed (Update-MgDomain -AuthenticationType Managed) can take up to 60 minutes.  
  <https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/migrate-from-federation-to-cloud-authentication>
- Cross-tenant access settings: B2B collaboration with all Entra orgs is allowed by default and B2B direct connect is blocked by default; organizational settings override defaults; inbound trust settings let your Conditional Access accept MFA, compliant-device and hybrid-joined claims from the partner's home tenant; configuring needs at least Security Administrator and P1 on the configuring tenant (both tenants for direct connect); automatic redemption suppresses the consent prompt only when both home-tenant outbound and resource-tenant inbound are checked; cross-tenant sync is enabled by inbound-only checkboxes in the TARGET tenant; changes are protected actions and logged under the CrossTenantAccessSettings audit category.  
  <https://learn.microsoft.com/en-us/entra/external-id/cross-tenant-access-overview>
- External collaboration settings (Entra ID > External Identities > External collaboration settings; Global Administrator or External Identity Provider Administrator): guest user access = same as members / limited (default: cannot enumerate users or groups) / restricted (own objects only); guest invite settings = anyone incl. guests / members and specific admin roles / only specific admin roles (User Administrator, Guest Inviter) / no one; Guest Inviter role works even when invites are limited to admin roles; allow-or-deny domain list; guest self-service sign-up toggle; external user leave settings require privacy info to be set; email OTP settings now live under All identity providers.  
  <https://learn.microsoft.com/en-us/entra/external-id/external-collaboration-settings-configure>

### Traps

| The wrong answer that looks right | Why it is wrong |
|---|---|
| Choosing Global Administrator (or User Administrator) whenever a task needs doing. | The stem almost always says 'least privileged'. Map task to the narrowest role: Password Administrator (non-admin password reset), Guest Inviter (invite guests), License Administrator (licenses), Groups Administrator (groups), Domain Name Administrator (domains), Organizational Branding Administrator (branding), Cloud Device Administrator (device settings), Authentication Administrator vs Privileged Authentication Administrator (MFA for non-admins vs anyone), Attribute Definition/Assignment Administrator (custom security attributes - GA cannot even read them by default). Verified at delegate-by-task. |
| 'Make the existing Helpdesk group role-assignable' or 'use a dynamic group for the Helpdesk Administrator role'. | isAssignableToRole can only be set on a NEW group and is immutable; role-assignable groups must have Assigned membership; creator must be at least Privileged Role Administrator. Any option that converts an existing group or uses a dynamic rule is wrong. |
| 'Set the user's usage location' as the universal fix for a failed group-based license assignment. | For group-based licensing users without a usage location inherit the tenant's location; the documented failure classes are insufficient licenses, conflicting service plans, missing dependencies, proxy address conflicts and 'usage location not allowed' for region-restricted plans, plus nested groups (members of nested groups get nothing). Usage location is mandatory for DIRECT per-user assignment. Read the stem: 'nested group' beats 'usage location'. |
| Picking Cloud Sync for hybrid Entra join / device sync or to configure PTA, or picking Connect Sync for disconnected forests. | Cloud Sync cannot synchronize devices (no hybrid join), cannot configure PTA or AD FS, and caps at 150K objects/domain and 50K group members; Connect Sync cannot handle disconnected forests and is a single point of failure. Match the stem's constraint to the comparison table. |
| Assuming PHS automatically takes over when PTA agents or AD FS go down. | PHS must already be enabled in parallel, and failover is a manual switch of the sign-in method in Microsoft Entra Connect; it does not happen automatically. The correct design answer is 'enable PHS alongside PTA/federation as a backup'. |
| Assuming a Global Administrator can edit users placed in a restricted management AU, or that an AU-scoped Helpdesk Administrator can reset passwords of members of a group that is in the AU. | Tenant-scoped GA/PRA cannot modify RMAU member objects unless they explicitly assign themselves a role scoped to that AU (auditable). AU scope over a group covers the group object only; users must be added directly to the AU for password/MFA management, and AU-scoped helpdesk roles never cover admin users. |
| Configuring cross-tenant trust, automatic redemption or B2B direct connect in only one tenant. | Direct connect requires both organizations to mutually enable inbound and outbound settings; automatic redemption only suppresses the consent prompt when the home tenant's OUTBOUND and the resource tenant's INBOUND settings are both checked; trust settings are configured INBOUND in the resource tenant. If CA requires MFA for direct connect users, MFA trust is mandatory. |
| Answering 'Azure AD B2C' for a new consumer-facing (CIAM) sign-up scenario, or using 'Azure AD', 'Connect-AzureAD/Connect-MsolService', or 'Entra Permissions Management' in an answer. | Azure AD B2C has been closed to new customers since 1 May 2025; the current answer is Microsoft Entra External ID in an EXTERNAL tenant configuration. Directory automation answers use Microsoft Graph PowerShell (Connect-MgGraph, New-MgUser, Get-MgUser, Update-MgDomain, New-MgDirectoryRoleMemberByRef); MSOnline/AzureAD modules are deprecated (March 2024). |

## D2 — Implement authentication and access management · 25-30%

*Revision budget: About 270 minutes (4.*

### Discriminators

**Security defaults** vs **Conditional Access**
- Security defaults are a free, tenant-wide on/off switch (MFA registration for all, MFA for admins and for Azure management, block legacy auth, block device code flow) with no customization; Conditional Access needs P1 and is fully customizable. They are mutually exclusive: you must disable security defaults to use CA, and Microsoft-managed policies are offered as the drop-in replacement. Toggled at Entra ID > Overview > Properties > Manage security defaults by at least a Conditional Access Administrator.
- **Tell:** 'Entra ID Free' / 'no premium licenses' / 'cannot afford P1' / 'simplest way to require MFA for everyone' → security defaults. 'Exclude a group', 'only from outside the corporate network', 'require compliant device', 'per-app' → Conditional Access, and the stem will usually say P1/P2 or E3/E5.

**Per-user MFA (Enabled / Enforced)** vs **Conditional Access MFA (grant control)**
- Per-user MFA is the legacy user-state model: Disabled → Enabled (user prompted to register; legacy auth still works) → Enforced (MFA every sign-in; legacy apps need app passwords). CA MFA never changes the user state — users correctly show as 'Disabled' on the per-user page. Microsoft: 'Don't enable or enforce per-user MFA if you use Conditional Access policies.' A Microsoft-managed policy exists to migrate tenants with <500 per-user MFA users.
- **Tell:** Any answer that says 'set the user's MFA status to Enforced' is the wrong answer when P1 is present. 'Users appear as Disabled on the per-user MFA page even though MFA is required' is not a problem — it is expected with CA. 'App passwords' in the stem signals legacy per-user MFA.

**Require multifactor authentication (grant)** vs **Require authentication strength (grant)**
- 'Require MFA' is a yes/no satisfied by ANY registered MFA combination, including SMS. 'Require authentication strength' names WHICH combinations are acceptable (built-in: Multifactor authentication, Passwordless MFA, Phishing-resistant MFA, or custom). The built-in MFA strength is equivalent to 'Require MFA', so the two grants cannot be selected together in one policy.
- **Tell:** 'phishing-resistant', 'only FIDO2/passkeys or Windows Hello', 'must not be able to use SMS', 'guests must use a specific method' → authentication strength. Plain 'require MFA' with no method constraint → Require MFA. Two-control answers that combine both grants are invalid.

**Passwordless MFA strength** vs **Phishing-resistant MFA strength**
- Both exclude passwords. Passwordless MFA includes Microsoft Authenticator phone sign-in; Phishing-resistant MFA does NOT — it is only Windows Hello for Business / platform credential, FIDO2 security key (passkey), and multifactor certificate-based authentication. TAP satisfies only the plain MFA strength.
- **Tell:** 'Users use Authenticator passwordless phone sign-in and are blocked by the policy' → the policy requires phishing-resistant; loosen to Passwordless MFA or issue passkeys. 'Authenticator push/number matching counts as phishing-resistant' is always false.

**Authentication methods policy (converged)** vs **Legacy MFA service settings / legacy SSPR authentication methods**
- The converged policy (Entra ID > Authentication methods > Policies) is the single place to enable, scope (include/exclude groups), and configure every method: Authenticator, passkey (FIDO2), TAP, SMS, voice, OATH tokens, CBA, email OTP, external methods. Legacy pages still exist and are migrated via the 'Manage migration' wizard (In progress → Complete; reversible). Security questions remain ONLY in the legacy SSPR policy. New tenants have all methods Off in the converged policy.
- **Tell:** 'Enable passkeys for a group', 'enable TAP', 'tenant-wide method settings' → authentication methods policy. 'Security questions' → legacy SSPR settings. 'MFA service settings / per-user MFA service settings / trusted IPs' → legacy, and usually the thing to migrate away from.

**Authentication Policy Administrator** vs **Authentication Administrator vs Privileged Authentication Administrator**
- Authentication Policy Administrator edits the TENANT policy (auth methods policy, TAP policy, smart lockout, password protection, registration campaign, per-user MFA page). Authentication Administrator manages PER-USER methods (create/delete a TAP, reset MFA) for non-admins only. Privileged Authentication Administrator does the same for anyone including Global Administrators. Global Reader can see that a TAP exists but not the code.
- **Tell:** 'policy', 'tenant-wide', 'enable the method' → Authentication Policy Admin. 'Reset this user's MFA / issue a TAP' → Authentication Admin. '...for a Global Administrator' / 'including administrators' → Privileged Authentication Admin. Global Administrator is offered and is wrong on least-privilege wording.

**Sign-in risk** vs **User risk**
- Sign-in risk = this particular authentication looks anomalous (anonymous IP, unfamiliar properties, atypical travel, password spray, token anomalies); remediated by a successful MFA. User risk = the account is probably compromised (leaked credentials — always High, offline, needs PHS to fix on-prem; anomalous token; attacker-in-the-middle); remediated by 'Require risk remediation' (secure password change after MFA, or session revocation for passwordless) — NOT SSPR. Microsoft's recommended levels: user risk High; sign-in risk Medium and High. Never put both risk conditions in one CA policy. Needs P2. Legacy ID Protection risk policies retire 1 October 2026.
- **Tell:** 'Leaked credentials', 'account compromised', 'change password' → user risk. 'Impossible travel', 'anonymous IP', 'unfamiliar sign-in properties', 'prove it's them' → sign-in risk. A stem that says 'the user changed their password from the Windows lock screen but risk stays High' → the on-prem password change setting or PHS is missing.

**Report-only** vs **On (enabled)**
- Report-only evaluates and logs (Report-only: Success / Failure / User action required / Not applied) but never prompts or blocks; results show in sign-in log 'Report-only' tab, the Policy impact view (Security Reader+), and the Insights workbook (needs Log Analytics). Limits: User Actions scope cannot be report-only; compliant-device policies in report-only can still trigger device-certificate prompts on macOS/iOS/Android. Templates and Microsoft-managed policies are created in report-only by default; Microsoft turns managed ones On no less than 30 days later. What If simulates a sign-in against enabled and report-only policies without any real sign-in.
- **Tell:** 'Without affecting users', 'assess impact before enforcing', 'which users would be blocked' → report-only (or What If if no sign-ins should occur at all). 'Policy has been report-only for months, auditor finding' → it protects nobody; switch On. 'Users on iPhones prompted to pick a certificate by a policy that isn't enforced' → report-only + compliant device.

**Sign-in frequency (session control)** vs **Continuous access evaluation (CAE)**
- Sign-in frequency is a TIMER: hours/days or Every time (5-minute clock-skew tolerance); default with no policy is a 90-day rolling window; PRT refreshes every 4 h on joined devices. CAE is an EVENT: Exchange/SharePoint/Teams/Graph subscribe to critical events (account disabled or deleted, password change/reset, MFA enabled, admin revokes refresh tokens, high user risk) and IP-based location changes; enforcement near real time, up to 15 min; CAE tokens live up to 28 h. CAE ignores country/GPS locations and MFA trusted IPs, does not support guests, and can only be disabled via a CA policy targeting All resources.
- **Tell:** 'Terminated employee must lose access immediately' / 'within minutes' → CAE (plus disable account and Revoke-MgUserSignInSession). 'Re-authenticate every 4 hours' / 'shared device' → sign-in frequency. 'Shorten token lifetime' is the distractor Microsoft explicitly calls the 'blunt object'.

**Persistent browser session** vs **Sign-in frequency**
- Persistent browser session (Always / Never) controls whether the 'Stay signed in?' cookie survives closing the browser — it is about browser cookie persistence on that device. Sign-in frequency controls how long ANY session (browser or native) can run before re-auth. Both live under Session controls; the 'Stay signed in?' prompt itself is toggled in Company branding.
- **Tell:** 'Kiosk / shared / unmanaged device must not stay signed in after closing the browser' → Persistent browser session: Never. 'Prompt again after N hours' → sign-in frequency. A stem about the 'Stay signed in?' checkbox appearing or not → company branding, not CA.

**IP-based named location (trusted)** vs **Country/region location (IP or GPS) and legacy MFA trusted IPs**
- Named locations: max 195, max 2000 ranges each, CIDR mask must be greater than /8, can be 'Mark as trusted' (feeds ID Protection accuracy; cannot delete while trusted). Country locations resolve by IP or by GPS from the Authenticator app (hourly prompt; jailbreak check; fails with passwordless-only users). Legacy 'MFA trusted IPs' are IPv4-only, live in the old MFA service settings, are not recommended, and appear as 'MFA Trusted IPs' in the location picker. Only IP-based named locations get real-time CAE enforcement.
- **Tell:** 'Block sign-ins from countries we don't operate in' → country location (include unknown countries/regions). 'Users get an hourly Authenticator prompt asking for location' → GPS-based country location. 'Corporate egress ranges' / 'exclude the office' → trusted named location. 'Skip MFA from the office using the MFA service settings' → legacy trusted IPs, wrong answer when named locations are offered.

**Authentication context** vs **Protected actions**
- Authentication context (c1–c99, Entra ID > Conditional Access > Authentication context, 'Publish to apps') is a tag a RESOURCE applies (SharePoint sensitivity labels, Defender for Cloud Apps session policy, custom apps via claims challenge, PIM role activation) so a CA policy can be enforced at the moment of the sensitive action rather than at sign-in. Protected actions (P1) are Entra PERMISSIONS (CA policy create/update/delete, cross-tenant access settings, named locations, hard delete of deleted items, auth-context update) that have an authentication context assigned, so admins must satisfy that CA policy before the Graph write succeeds. Protected actions REQUIRE an authentication context; Azure PowerShell cannot step up and fails.
- **Tell:** 'Step-up when opening a labeled SharePoint site / activating a PIM role / a specific app operation' → authentication context. 'Require phishing-resistant MFA before anyone can modify Conditional Access policies or permanently delete users, regardless of role' → protected actions. Stems that need it 'independent of the role' or 'even for Global Admins' → protected actions.

**Conditional Access template** vs **Microsoft-managed Conditional Access policy**
- Templates (Entra ID > Conditional Access > Create new policy from templates; categories Secure foundation, Zero Trust, Remote work, Protect administrator, Emerging threats, AI Agents) are created by YOU, in report-only, excluding only the creating user; you can edit fully, export/import JSON. Microsoft-managed policies are created by MICROSOFT in eligible tenants ('Created by: Microsoft'), start report-only, are turned On by Microsoft no less than 30 days later unless set Off, can only have identities excluded or state changed, cannot be renamed or deleted (duplicate to customize).
- **Tell:** 'A policy appeared that we didn't create' / 'cannot delete the policy' / 'policy will be enabled in 30 days' → Microsoft-managed. 'Fastest way to deploy Microsoft-recommended baseline policies' → templates. 'Break-glass accounts not excluded after using a template' → correct, templates only exclude the creator; edit the policy.

**Password change for risk remediation** vs **SSPR (password reset) and password writeback**
- Risk remediation ('Require risk remediation' or the older 'Require password change' grant) is MFA + change of a KNOWN password inside Conditional Access; it does NOT use SSPR and needs all users pre-registered for MFA (unregistered users are blocked). SSPR is recovery of a FORGOTTEN password with 1 or 2 configurable gates for users; administrators are always two-gate, cannot use security questions, and can be excluded via AllowedToUseSspr=false. Password writeback (Connect Sync or Cloud Sync) is what makes either flow land in on-prem AD and works with PHS, PTA and federation; hybrid risky users need writeback (or PHS + 'Allow on-premises password change to reset user risk').
- **Tell:** 'Risky user' / 'leaked credentials' → risk remediation grant, not SSPR. 'Users forget passwords, reduce helpdesk calls' → SSPR. 'Hybrid users reset in the cloud but the domain-joined laptop still wants the old password' → password writeback. 'Admins can't use security questions' → by design (two-gate), not a bug.

**Entra smart lockout** vs **On-premises AD DS account lockout (and global vs custom banned password list)**
- Smart lockout is always on for every tenant: default 10 failed attempts (3 in US Gov), 60-second lockout that grows; tracks the last 3 bad-password hashes so the same wrong password doesn't count again (not with PTA); familiar and unfamiliar locations have separate counters; customizing needs P1 (Entra ID > Authentication methods > Password protection, Authentication Policy Admin). With PTA the Entra threshold must be LOWER than the AD DS threshold and the Entra duration LONGER, so cloud lockout absorbs sprays before AD locks. Password protection: global banned list is free and cannot be turned off; custom list (max 1000 base terms) needs P1; scoring — normalize, fuzzy match edit-distance 1, substring match on names ≥4 chars, ≥5 points to accept; on-prem DC agent runs Audit before Enforce.
- **Tell:** 'Users are being locked out of AD by password spray against Entra' → set smart lockout threshold below AD's and duration above AD's. 'Ban the company name and product names' → custom banned list, P1. '"C0ntos0Blank12" rejected' → scoring under 5 points. 'Proxy servers/DC agent, Audit mode' → on-prem password protection.

**Temporary Access Pass (TAP)** vs **Passkey (FIDO2) — device-bound vs synced**
- TAP is a time-limited BOOTSTRAP credential (default 1 h, max 8 h, allowed 10 min–30 days, 8–48 chars, one-time or multi-use, one TAP per user, cannot be issued to external guests, tokens issued during TAP sign-in are capped at TAP expiry). A one-time TAP must complete passwordless registration within 10 minutes. Passkeys are the DESTINATION credential: origin-bound key pairs; device-bound (Authenticator, security key, Entra passkey on Windows) vs synced (iCloud Keychain, Google Password Manager); enforcing attestation in a passkey profile excludes synced passkeys. From 1 Sep 2026 passkeys are auto-enabled for SMS/voice users; Microsoft-provided SMS/voice retire 1 Feb 2027 with no opt-out from the blocking passkey prompt.
- **Tell:** 'New hire, no password, no phone registered, must register a passkey' → TAP. 'Registration failed because it took longer than 10 minutes' → one-time TAP limit; use multi-use. 'Regulated users / highest assurance / must verify device model' → device-bound with attestation (security keys). 'Lowest-cost phishing-resistant MFA for everyone' → synced passkeys.

**Application-enforced (device-enforced) restrictions** vs **Conditional Access App Control (Defender for Cloud Apps)**
- App-enforced restrictions is a session control that passes device state to SharePoint Online / Exchange Online / M365 so the APP itself gives a limited (no download/print/sync) experience on unmanaged devices; configured on the app side (SharePoint 'Control access from unmanaged devices'). Conditional Access App Control routes the session through the Defender for Cloud Apps reverse proxy so ACCESS and SESSION policies (block download, apply label, monitor) apply in real time to any SAML/OIDC app; needs Defender for Cloud Apps licensing.
- **Tell:** 'Users on unmanaged devices may read but not download from SharePoint/OWA' → app-enforced restrictions. 'Block download / monitor session / third-party SaaS app / real-time' → Conditional Access App Control + Defender for Cloud Apps session policy.

**Global Secure Access — Microsoft traffic profile (P1/P2)** vs **Microsoft Entra Internet Access vs Microsoft Entra Private Access (separate licenses / Entra Suite)**
- Global Secure Access is the umbrella for Microsoft's SSE. The Microsoft (M365) traffic profile, compliant-network check, universal tenant restrictions, source IP restoration and M365 enriched logs are included in Entra ID P1/P2. Internet Access (secure web gateway: web-category and FQDN filtering, TLS inspection, threat intelligence) and Private Access (ZTNA VPN replacement: Quick Access, per-app TCP/UDP access, private DNS, Kerberos SSO; successor to Application Proxy) each need their own license or the Entra Suite. The Windows client requires an Entra joined, hybrid joined, or registered device (registered = Private Access only), Windows 10 LTSC 2021+/11 64-bit, local admin; AVD multi-session unsupported; download at Global Secure Access > Connect > Client download as Global Secure Access Administrator.
- **Tell:** 'Only allow M365 access from devices running the GSA client' → compliant network named location (P1). 'Block social media category' → Internet Access. 'Replace VPN to reach an on-prem SQL server by IP' → Private Access (Quick Access / per-app). 'Prevent users signing in to a personal tenant from corporate devices' → universal tenant restrictions.

**External authentication methods (EAM)** vs **Custom controls (preview, deprecated path)**
- EAM is an OIDC-based integration where a third-party MFA provider issues the second factor and Entra records an MFA claim; it is configured in the authentication methods policy and SATISFIES 'Require multifactor authentication', but NOT 'Require authentication strength' (not even the built-in MFA strength). Custom controls redirect to the provider and never produce an MFA claim, so they don't satisfy MFA requirements or Microsoft-managed policies; Microsoft says migrate custom controls to EAM.
- **Tell:** 'We use Duo/Okta Verify for MFA and Microsoft-managed MFA policies keep prompting' → custom control; migrate to external authentication method. 'External method works with Require MFA but fails with phishing-resistant strength policy' → expected; EAM doesn't satisfy strengths.

**Windows Hello for Business** vs **Passkey (FIDO2) security key / Microsoft Entra Kerberos**
- WHfB is a device-bound asymmetric KEY or CERTIFICATE credential unlocked by PIN/biometric — two-factor by itself, satisfies 'Require MFA' and the Phishing-resistant strength (listed as 'Windows Hello for Business or platform credential'), and is not the same thing as a FIDO2 security key even though Windows can also expose Hello via WebAuthn. Microsoft Entra Kerberos is the piece that lets a cloud credential (FIDO2 key or WHfB cloud Kerberos trust) reach on-prem AD resources: Set-AzureADKerberosServer (AzureADHybridAuthenticationManagement module, needs Hybrid Identity Administrator + Domain/Enterprise Admin) creates the krbtgt_AzureAD account; Entra issues a partial TGT (SID only) that the client exchanges at a writable DC; rotate the key on the same schedule as krbtgt; needs Server 2016+ DCs, Windows 10 2004+, and onPremisesSamAccountName/DomainName/SecurityIdentifier synced.
- **Tell:** 'Sign in to Windows with a FIDO2 key and open an on-prem file share without a password' → Microsoft Entra Kerberos (Set-AzureADKerberosServer). 'Cloud Kerberos trust' → WHfB deployment model that also needs Entra Kerberos. 'Explainer says WHfB is FIDO2' → treat as loose; on the exam WHfB is a 'platform credential' inside the phishing-resistant strength.

**Revoke sessions / Revoke-MgUserSignInSession** vs **Disable account / delete devices / CAE**
- Revoking refresh tokens (Users > user > Revoke sessions, or Revoke-MgUserSignInSession) stops NEW access tokens but an already-issued access token lives up to 1 hour unless the app is CAE-capable (then revocation is a critical event, enforced within minutes). Disabling the account (Update-MgUser -AccountEnabled:$false) blocks new sign-ins and is itself a CAE critical event. Disabling devices (Update-MgDevice) prevents PRT use. Hybrid: disable in AD and reset the password twice (pass-the-hash), and remember sync latency. Microsoft's emergency sequence: disable account → revoke sessions → disable devices (+ on-prem steps).
- **Tell:** 'Compromised account, needs immediate action, list the steps' → disable, revoke refresh tokens, disable devices. 'User still reads mail 40 minutes after revoke' → non-CAE client, access token lifetime. 'Re-enable a user but Exchange still says disabled' → known 35–40 minute enablement latency.

### High-yield facts

- Multiple grant controls default to 'Require all the selected controls' (AND); you must pick 'Require one of the selected controls' for OR. Block beats grant; the approved-client-app grant retired March 2026 (use app protection policy); 'Require password change' must target All resources and cannot be combined with other controls; 'Require risk remediation' auto-selects Require authentication strength + Sign-in frequency Every time. Validation order across policies is MFA → device state → terms of use.  
  <https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-grant>
- Three built-in authentication strengths: Multifactor authentication, Passwordless MFA, Phishing-resistant MFA. Phishing-resistant = Windows Hello for Business/platform credential, FIDO2 security key (passkey), multifactor CBA. Authenticator phone sign-in is Passwordless but not phishing-resistant; TAP satisfies only the MFA strength; SMS sign-in, single-factor CBA, QR code, and plain password satisfy none. You cannot select 'Require MFA' and 'Require authentication strength' in the same policy; email OTP (guest) is unsupported; strengths are evaluated after primary authentication, so a user can still type a password first.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/concept-authentication-strengths>
- TAP policy defaults: default lifetime 1 hour, maximum 8 hours, allowed 10 minutes–30 days (43,200 min), length 8–48, one-time use False by default. Enabling the policy needs Authentication Policy Administrator; issuing a TAP needs Authentication Administrator (Privileged Authentication Administrator for admins); Global Reader sees it exists but not the code. A one-time TAP must finish passwordless registration within 10 minutes; each user can hold only one TAP; TAP cannot be added to external guests; a TAP is preferred over federation; TAP cannot be used with the NPS extension or AD FS adapter; tokens issued during a TAP sign-in are capped at TAP expiry but existing sessions are not retroactively killed.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/howto-authentication-temporary-access-pass>
- Smart lockout defaults: 10 failed attempts (3 in Azure US Government), first lockout 60 seconds and growing; last three bad-password hashes are not double-counted (not available with PTA); separate counters for familiar vs unfamiliar locations; customizing requires P1 and Authentication Policy Administrator at Entra ID > Authentication methods > Password protection. With PTA: Entra threshold must be LESS than AD DS threshold (e.g., 10 vs 20) and Entra duration LONGER than AD DS duration (e.g., 120 s vs 1 min). Admin can unlock without waiting; 'I forgot my password' in SSPR resets the lockout timer, 'I know my password' does not.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/howto-password-smart-lockout>
- Password protection: the global banned list is applied to every tenant, cannot be disabled, and is not built from third-party breach lists; the custom banned list needs P1 (P1/P2 also for synced users even for the global list), holds max 1,000 base terms, and evaluation is normalize (lower-case, 0→o, 1→l, $→s, @→a) → fuzzy match at edit distance 1 → substring match on first/last/tenant name of ≥4 chars → score: each banned term 1 point, each other character 1 point, need ≥5 points. Example: 'C0ntos0Blank12' = 4 points, rejected.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/concept-password-ban-bad>
- SSPR: users need 1 or 2 registered methods as configured; Authenticator cannot be the only method when one is required. Administrators are enabled for SSPR by default under an unchangeable two-gate policy (two methods, security questions prohibited; office/mobile voice prohibited on free/trial), independent of the authentication methods policy; disable admin SSPR with Update-MgPolicyAuthorizationPolicy -AllowedToUseSspr:$false. Cloud password policy: 8–256 chars, 3 of 4 character classes, default no expiry (90 days for tenants created before 2021), lockout 10/1 min.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/concept-sspr-policy>
- Password writeback: when enabled, federated, pass-through authentication, and password hash synchronized users can all reset; when disabled none of them can. Writeback can be configured for Connect Sync or Cloud Sync; 'Allow users to unlock accounts without resetting their password' is a separate toggle; SSPR performs the equivalent of an admin reset in AD so third-party password filters must apply to admin resets. Microsoft-account (Hotmail/Outlook.com) guests cannot use Entra SSPR.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/concept-sspr-howitworks>
- Risk policies in Conditional Access: never combine sign-in risk and user risk conditions in one policy. Microsoft recommends user risk High → 'Require risk remediation' (auto-applies Require authentication strength + Sign-in frequency Every time; passwordless users get sessions revoked, password users do MFA then secure password change); sign-in risk Medium and High → built-in MFA strength + Sign-in frequency Every time. Users must be MFA-registered first (otherwise blocked), hybrid users need password writeback; P2 (or Entra Suite) required; Conditional Access Administrator is least privilege to create the policy. Legacy ID Protection risk policies are retired on 1 October 2026 — migrate to CA.  
  <https://learn.microsoft.com/en-us/entra/id-protection/howto-identity-protection-configure-risk-policies>
- Leaked credentials is a user-risk detection, calculated offline, always High, available on Free/P1, and requires password hash synchronization for on-premises passwords; a cloud password reset remediates it for cloud and on-prem passwords when PHS is on. Real-time sign-in detections include anonymous IP (non-premium), unfamiliar sign-in properties, verified threat actor IP, suspicious MFA approval; atypical travel, malicious IP, password spray (offline or real-time), token issuer anomaly are P2. Without P2 you only see 'Additional risk detected' with riskEventType 'generic'.  
  <https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks>
- Continuous access evaluation: critical events are user deleted/disabled, password changed/reset, MFA enabled for the user, admin revokes all refresh tokens, high user risk (SharePoint does not support user-risk events); enforcement near real time with up to 15 minutes latency, IP-location enforcement is instant; CAE-capable sessions get tokens up to 28 hours and ignore configurable token lifetime; non-CAE clients keep the 1-hour default. CAE only understands IP-based named locations (not country/region or MFA trusted IPs), stops enforcing location changes above 5,000 total IP ranges, does not support guest users, and can be disabled only in a policy scoped to All resources with no conditions. Policy/group-membership changes can take up to a day to reach resource providers; use Revoke-MgUserSignInSession to force it.  
  <https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-continuous-access-evaluation>
- Session lifetime: the Entra default is a rolling 90-day sign-in frequency ('don't ask users to provide their credentials if the security posture of their sessions hasn't changed'); sign-in frequency now applies to MFA too; on joined/hybrid-joined devices the PRT refreshes every 4 hours on unlock, which is what satisfies SIF; 'Every time' has a 5-minute clock-skew tolerance and can loop without MFA; persistent browser session works with the 'Stay signed in?' prompt controlled by company branding; disable 'Remember MFA on trusted devices' before using SIF; configurable token lifetime for refresh/session tokens was retired 30 January 2021.  
  <https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-session-lifetime>
- Report-only mode results are Report-only: Success / Failure / User action required / Not applied (plus Success / Failure / Not applied for enforced policies), visible in the sign-in log Conditional Access and Report-only tabs, the Policy impact view (Security Reader+), and the Insights and Reporting workbook (needs P1 + Log Analytics receiving sign-in logs). Report-only cannot be used for the User Actions scope, and report-only compliant-device policies can prompt macOS/iOS/Android users for a device certificate — exclude those platforms. Classic policies stopped enforcing after 10 July 2024 and cannot be re-enabled once disabled.  
  <https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-report-only>
- Templates (Entra ID > Conditional Access > Create new policy from templates) are created in report-only by default and exclude ONLY the user who created them — you must add break-glass accounts yourself; JSON can be exported and re-imported with 'Upload policy file'. Microsoft-managed policies are created by Microsoft in report-only, turned On no less than 30 days later unless set Off, allow only exclusions and state changes, cannot be renamed or deleted; the set includes block legacy authentication, block device code flow, MFA for admins accessing admin portals, MFA for all users, MFA for per-user-MFA users (<500 users), MFA and reauthentication for risky sign-ins (P2), block/require remediation for high-risk users (P2), and the Baseline security mode 'phishing-resistant for admins'.  
  <https://learn.microsoft.com/en-us/entra/identity/conditional-access/managed-policies>
- Security defaults (free): require MFA registration for all users, MFA for 16 admin roles, MFA for Azure Resource Manager access, block legacy authentication (including Exchange ActiveSync basic auth), and block device code flow (all new tenants from 1 July 2026). Toggle at Entra ID > Overview > Properties > Manage security defaults as at least Conditional Access Administrator; must be disabled to use Conditional Access, and Microsoft-managed policies replace them; sync accounts (Directory Synchronization Accounts role) are excluded; users show 'Disabled' on the per-user MFA page; the 14-day MFA registration grace period was removed 29 July 2024.  
  <https://learn.microsoft.com/en-us/entra/fundamentals/security-defaults>
- Protected actions (P1) attach a Conditional Access authentication context to specific Entra permissions so the CA policy is enforced at the moment of the action, independent of role: Conditional Access policy create/update/delete, all cross-tenant access policy updates (B2B collaboration, direct connect, tenant restrictions, cross-cloud meetings), named-location create/update/delete, hard delete of soft-deleted objects (microsoft.directory/deletedItems/delete), and authentication-context updates on RBAC resource actions. Configure as Conditional Access Administrator or Security Administrator: create the auth context and policy first, then add the protected action, then test; Azure PowerShell and creating new terms-of-use/custom controls fail under protected actions; keep an emergency account excluded.  
  <https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/protected-actions-overview>
- Passkeys become the default sign-in experience from 1 September 2026: users enabled for SMS or voice in the authentication methods policy or legacy MFA settings are auto-enabled for passkeys and nudged by a Microsoft-managed registration campaign (unlimited snoozes by default). Microsoft-provided SMS and voice retire 1 February 2027; afterwards users whose only MFA method is SMS/voice get a BLOCKING passkey-registration prompt with no opt-out; customer-managed telecom providers via the Microsoft Security Store from 30 October 2026. A temporary opt-out (1 Sep 2026–1 Feb 2027) is set with PATCH /beta/policies/authenticationmethodspolicy optOutSettings.passkeyDynamicMigration=true.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/concept-sms-voice-retirement>
- Registration campaign (Entra ID > Authentication methods > Registration campaign, Authentication Policy Administrator): states Microsoft managed / Enabled / Disabled; targets one method at a time — Passkey (FIDO2) or Microsoft Authenticator; Authenticator nudge fires only after MFA by SMS/voice, passkey nudge after any MFA and only if no local passkey exists for that OS+browser; snooze 0–14 days; 'Limited number of snoozes' = 3 then mandatory; Microsoft-managed defaults are 1-day snooze, limited (3) for Authenticator and unlimited for passkeys; guests are not nudged for passkeys; users under a 'Register security information' CA block or a terms-of-use interrupt are not nudged.  
  <https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-registration-campaign>
- Emergency revoke sequence (Entra): clear 'Account enabled' (User Administrator; Privileged Authentication Administrator for admin accounts), then Revoke sessions / Revoke-MgUserSignInSession -UserId, then disable registered devices via Get-MgUserRegisteredDevice | Update-MgDevice -AccountEnabled:$false (Cloud Device Administrator). Hybrid: Disable-ADAccount and reset the AD password twice (pass-the-hash mitigation). Access tokens still last up to 1 hour unless the app is CAE-capable; app session cookies are governed by the app. Azure AD/MSOnline PowerShell modules are deprecated (30 March 2024).  
  <https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access>
- Global Secure Access licensing: the Microsoft traffic profile, compliant-network check, universal tenant restrictions, source IP restoration, and M365 enriched logs are in Entra ID P1/P2; Internet Access (web-category/FQDN filtering, TLS inspection, threat intelligence, DLP) and Private Access (VPN replacement, Quick Access, per-app TCP/UDP, private DNS, Kerberos SSO) are standalone licenses or Entra Suite, and their users still need P1/P2; remote networks need ≥50 combined P1 + Internet Access licenses. ## D3 — Plan and implement workload identities · 20-25%

*Revision budget: About 240 minutes total for this domain, split across two sittings.*

### Discriminators

**App registration (application object)** vs **Enterprise application (service principal)**
- The application object is the single global blueprint living in the home tenant; the service principal is the per-tenant local instance that actually holds consent, role assignments, user/group assignment and sign-in settings. Deleting the app object deletes only the home-tenant SP, and restoring the app registration does NOT restore its SP.
- **Tell:** 'Where do you configure redirect URIs / secrets / exposed API / app roles definition' → App registrations. 'Who in OUR tenant can use it / consented permissions / assignment required / disable sign-in / a third-party gallery app' → Enterprise applications. If the stem says the app was built by another company, you only ever touch the SP.

**Delegated permission (scp claim)** vs **Application permission (roles claim)**
- Delegated = acting on behalf of a signed-in user; effective rights are the intersection of the user's rights and the granted scope; users can consent to low-impact ones. Application = app acts as itself with no user; full tenant-wide permission; ONLY admins can consent; static list only (no dynamic consent). Consent result: oauth2PermissionGrant vs appRoleAssignment.
- **Tell:** 'daemon', 'background service', 'nightly job', 'no user signed in', 'runs unattended' → application permission + admin consent. 'on behalf of the signed-in user', 'only what the user can already see', 'least privilege for an interactive app' → delegated. A token screenshot with `scp` = delegated, with `roles` = application.

**System-assigned managed identity** vs **User-assigned managed identity**
- System-assigned is created with and deleted with one Azure resource, cannot be shared, and its SP name equals the resource name. User-assigned is a standalone Azure resource with independent lifecycle, can be attached to many resources, can be pre-authorized before compute exists, and is the type Microsoft now recommends by default.
- **Tell:** 'many VMs/functions need the same access', 'permissions must survive redeploy/recreation', 'grant access before the resource is created', 'resources recycled frequently' → user-assigned. 'single resource, delete identity with the resource, simplest' → system-assigned.

**Managed identity** vs **Service principal with app registration + secret/certificate**
- Managed identity is a special SP type with NO application object, credentials handled entirely by Azure, no cost, cannot be edited directly, and only usable by workloads running on Azure compute. An app registration SP needs you to hold a credential (secret/cert) or a federated credential, works anywhere including multitenant.
- **Tell:** 'workload runs on Azure App Service/VM/Functions/AKS and must call Key Vault/Storage/Graph with no stored credentials' → managed identity. 'runs on-premises', 'runs in AWS/GCP', 'multitenant SaaS', 'needs to be used from a developer laptop' → service principal (prefer federated credential > certificate > secret).

**Workload identity federation (federated identity credential)** vs **Client secret / certificate**
- Federation lets an external OIDC issuer's token (GitHub Actions, Kubernetes, GCP, AWS, SPIFFE, or an Azure managed identity) be exchanged for an Entra token — nothing is stored anywhere. Issuer + subject + audience must match case-sensitively; no wildcards; max 20 per app or user-assigned MI; a wrong subject is accepted at creation and only fails silently at exchange time. Secrets and certificates are stored credentials that expire.
- **Tell:** 'eliminate secrets from the CI/CD pipeline', 'GitHub Actions must deploy without a stored secret', 'no credential rotation', 'Kubernetes pod outside Azure' → workload identity federation. 'the pipeline stopped working after 12/24 months and nothing changed' → expired client secret.

**Managed identity (Azure)** vs **Group Managed Service Account (gMSA) / sMSA (on-prem AD DS)**
- Both remove human password handling, but gMSA is an Active Directory account for Windows services running on domain-joined servers (server farms, load-balanced services; the DC manages the password). Managed identity is an Entra service principal for Azure-hosted resources. Microsoft guidance: on-prem → gMSA when possible, else sMSA, computer account, then user account; Azure → managed identity, else service principal; never a user account as a service account.
- **Tell:** 'Windows service on a farm of on-premises servers', 'IIS app pool', 'scheduled task on domain-joined server', 'password must be managed by the domain' → gMSA. 'Azure resource needs to authenticate to another Azure resource' → managed identity. 'service is not hosted in Azure' → service principal.

**User consent** vs **Admin consent**
- User consent is a single user granting delegated permissions for their own data; tenant setting has three modes (Do not allow / Allow for verified publishers + classified low-impact permissions [microsoft-user-default-low] / Allow all [microsoft-user-default-legacy]). Admin consent grants for the whole organization and is mandatory for all application permissions, high-privilege delegated permissions, and any app with 'assignment required = Yes'. Changing the tenant setting never touches existing grants.
- **Tell:** 'application permission' or 'assignment required' → admin consent regardless of user settings. 'users are consenting to malicious/phishing apps' → restrict user consent to verified publishers + low impact. 'grant for the entire organization' → admin consent.

**Admin consent workflow** vs **Disabling user consent outright**
- The workflow keeps users blocked from self-consent but gives them a Request button that emails designated reviewers who approve/deny within a configurable expiry (up to an hour to activate). Reviewers must independently hold the rights to consent — being a reviewer grants nothing — and only Global Administrators can approve requests for Microsoft Graph application permissions. Simply disabling user consent produces a dead-end error and helpdesk tickets.
- **Tell:** 'users should be able to request access to apps they can't consent to', 'reduce helpdesk tickets while blocking user consent', 'designate reviewers' → enable admin consent workflow (Enterprise apps > Consent and permissions > Admin consent settings).

**Application Administrator** vs **Cloud Application Administrator**
- Identical rights over app registrations and enterprise apps (create, manage, add credentials, consent to delegated permissions and non-Graph application permissions) EXCEPT that only Application Administrator can manage Application Proxy (download connector, connector groups, publish app). Neither can manage Conditional Access, and neither can grant admin consent to Microsoft Graph application permissions — that needs Privileged Role Administrator (or Global Admin).
- **Tell:** 'least privileged role to publish an on-premises app via Application Proxy / configure a connector group' → Application Administrator. 'manage all apps but must NOT be able to touch App Proxy' → Cloud Application Administrator. 'grant admin consent for Microsoft Graph application permission' → Privileged Role Administrator.

**Single sign-on (SSO)** vs **Automatic provisioning (SCIM)**
- SSO is authentication — Entra issues the SAML/OIDC assertion so the user needs no second password. Provisioning is lifecycle — Entra calls the app's SCIM 2.0 /Users and /Groups endpoints to create, update, disable and delete accounts on an initial then incremental cycle. An app can have either without the other.
- **Tell:** 'users can sign in but the app says account not found' → provisioning missing or user out of scope. 'leavers still have active accounts in the SaaS app' → no deprovisioning; configure provisioning. 'sign-in prompts for the app's own password' → SSO not configured.

**Password-based SSO** vs **Linked SSO (and SAML/OIDC)**
- Password-based = Entra vaults the credential and replays it into the app's HTML sign-in form; works for apps with no federation support and for shared accounts (Entra stores the shared password so users never learn it). Linked = just a tile that sends the user to a URL already federated elsewhere (e.g., AD FS) — Entra performs NO authentication. SAML/OIDC = real federation and should be chosen whenever the app supports it.
- **Tell:** 'app supports neither SAML nor OpenID Connect', 'shared social-media account', 'HTML login page' → password-based. 'app already uses AD FS / another IdP, just needs to appear in My Apps' → linked. 'app supports SAML' → SAML (never password-based).

**Assignment required = Yes** vs **Visible to users / Enabled for users to sign in**
- Assignment required controls WHO gets a token (users, groups AND other apps requesting tokens; Global Admins bypass it; it also forces admin consent). Visible to users only hides/shows the tile in My Apps and the M365 launcher — unassigned users never see it regardless. Enabled for users to sign in = No stops ALL token issuance, including service principals using application permissions — the emergency off switch.
- **Tell:** 'only members of a group may access the SaaS app' → assignment required Yes + assign group. 'immediately stop anyone and anything using the app' → Enabled for users to sign in = No. 'everyone can use it but only Finance should see the tile' → assignment required No + assign Finance + visible Yes.

**App roles (roles claim)** vs **Security groups (groups claim)**
- App roles are defined in the app registration (Display name, Allowed member types Users/Groups and/or Applications, Value = the string in the token), assigned to users/groups in Enterprise apps > Users and groups (or to other SPs as application permissions), travel with the app across tenants, and are deleted with the registration. Groups are tenant-scoped, survive app deletion, and their IDs differ per tenant. A role assigned to a group that contains an SP is NOT emitted for that SP; a disabled role keeps flowing in tokens until assignments are removed.
- **Tell:** 'the app must be portable to other tenants', 'authorization inside the app should not depend on group IDs', 'token must contain roles claim' → app roles. 'define application permissions for a custom API' → app role with Allowed member types = Applications.

**Conditional Access for workload identities** vs **Microsoft Entra ID Protection risky workload identities**
- CA for workload identities ENFORCES: policies target single-tenant service principals in your tenant (not multitenant apps, not Microsoft/SaaS apps, not managed identities), SP must be added directly (group membership is ignored), conditions are Location and Service principal risk, and the ONLY grant is Block. Requires Workload Identities Premium (Microsoft Entra Workload ID) to create/modify. ID Protection DETECTS: detections (leaked credentials, suspicious sign-ins, anomalous SP activity, suspicious API traffic, malicious/suspicious application, threat intelligence) are shown to everyone but full details need Workload Identities Premium; remediation = confirm compromised / dismiss / disable SP, rotate credentials (x509 recommended) and Key Vault secrets.
- **Tell:** 'block the service principal when its risk is high / from outside the datacenter IP range' → CA for workload identities (Block). 'investigate / view detections / confirm compromised' → ID Protection > Risky workload identities. If the stem says 'managed identity' or 'multitenant app' → out of scope for both; use access reviews instead.

**Conditional Access app control (Defender for Cloud Apps session/access policies)** vs **Application-enforced restrictions (CA session control)**
- App control routes the browser session through Defender for Cloud Apps (reverse proxy, *.mcas.ms suffix, or Edge in-browser protection) and can block download/upload/copy/print, label on download, block malware, or require step-up via authentication context — works for any SAML 2.0/OIDC app, browser sessions only. Application-enforced restrictions just has Entra pass device-compliance info to SharePoint Online / Exchange Online / M365 idle-session timeout so THOSE apps downgrade to a limited (web-only, no download) experience on unmanaged devices.
- **Tell:** 'block downloads from Salesforce/Box/any third-party SaaS on unmanaged devices', 'monitor session', 'block upload of unlabeled files' → Conditional Access app control + session policy. 'limited web-only experience in SharePoint/Exchange on non-compliant devices' → Use app enforced restrictions.

**Access policy (Defender for Cloud Apps)** vs **Session policy (Defender for Cloud Apps)**
- Access policy = allow/block the whole sign-in at connection time, evaluated for browsers AND native/mobile clients (e.g., block Dropbox native client, block Salesforce from unmanaged devices). Session policy = allow the sign-in but control what happens inside the browser session in real time (block download/cut/copy/print, protect on download, block custom activities, require authentication context); browser only, not native or the Teams desktop app.
- **Tell:** 'block access entirely from native clients' → access policy. 'allow access but prevent downloading sensitive files / require a label on download / monitor' → session policy.

**Cloud discovery (Shadow IT)** vs **App connectors (API-connected sanctioned apps)**
- Cloud discovery analyzes firewall/proxy traffic logs (snapshot = manual upload; continuous = Defender for Endpoint integration, log collector, or SWG integration) against a catalog of 31,000+ apps scored on 90+ risk factors to find unsanctioned use. App connectors use the SaaS vendor's API to get accounts, activities, files and permissions from apps you already sanction (Microsoft 365, Salesforce, Box, Google Workspace, AWS) and to take governance actions.
- **Tell:** 'find which unsanctioned cloud apps employees are using', 'upload firewall logs', 'risk score of an app' → cloud discovery / cloud app catalog. 'get activity log and user list from Salesforce/Box', 'revoke a user's token in an app', 'scan files in the app' → connect the app (app connector).

**OAuth app policies (Defender for Cloud Apps app governance)** vs **Entra user consent settings**
- Entra consent settings PREVENT future grants. Defender for Cloud Apps OAuth app policies DETECT and RESPOND to apps already authorized in your tenant (filter by permission level, community use rarity, number of users; built-in anomaly policies for misleading app/publisher names and malicious consent); marking a permission as Banned disables the enterprise application.
- **Tell:** 'alert when an app with high-permission level is authorized by more than N users', 'revoke an OAuth app authorized by users', 'misleading publisher name' → Defender for Cloud Apps OAuth app policy. 'stop users from consenting in the first place' → Entra user consent settings.

**Object ID of the service principal (Enterprise apps > Overview)** vs **Object ID of the app registration / Application (client) ID**
- Three identifiers. Application (client) ID is the same across all tenants and is what code uses (AZURE_CLIENT_ID). The app registration's Object ID identifies the application object (used e.g. for federated credential Graph calls). The enterprise app's Object ID identifies the service principal and is what Conditional Access for workload identities, role assignments and consent operate on.
- **Tell:** 'which ID do you use in a Conditional Access workload identity policy' → the service principal Object ID from Enterprise apps (the docs explicitly say the App registrations Object ID cannot be used). 'value for AZURE_CLIENT_ID in the GitHub workflow' → Application (client) ID.

| 'Reset the compromised user's password' as the fix for a malicious app still reading their mailbox after an illicit consent grant. | OAuth grants are independent of the credential. Revoke the service principal's grants (Admin consent tab in the portal; user-consent grants only via Graph DELETE /oAuth2PermissionGrants/{id} or Remove-MgOauth2PermissionGrant) and revoke refresh tokens/sessions; then restrict user consent to verified publishers + low impact so it cannot be re-granted. |

Anything outside Azure uses an app registration/service principal; the secretless answer is a federated identity credential (workload identity federation), and the secretful fallback order is certificate before client secret. |
| 'Add the service principals to a security group and target the group in the Conditional Access policy' (or 'require MFA for the service principal'). | CA policies assigned to a group are NOT enforced for service principals in it — each SP must be selected directly under Users or workload identities > Workload identities. Workload identities cannot do MFA; the only available grant is Block. Managed identities and multitenant/SaaS apps cannot be targeted at all. |
| 'Assign Cloud Application Administrator' as the least-privileged role to publish an app through Application Proxy or create a connector group. | Cloud Application Administrator is Application Administrator minus Application Proxy. App Proxy tasks need Application Administrator. Conversely, when the stem says the admin must NOT be able to touch App Proxy, Cloud Application Administrator is the answer. |
| 'Application Administrator can grant admin consent to the app's Microsoft Graph application permissions (e.g., User.ReadWrite.All).' | Both Application Administrator and Cloud Application Administrator are explicitly excluded from consenting to Microsoft Graph (and Azure AD Graph) application permissions. That requires Privileged Role Administrator (or Global Administrator) — and in the admin consent workflow only Global Administrators can approve such requests. |
| 'Deleting the app registration removes the app from all customer tenants' / 'restoring the deleted app registration brings back its enterprise application and consent'. | Deleting the application object removes only the home-tenant service principal; SPs already created in other tenants persist. Restoring the app registration does not restore its service principal or the consent grants attached to it. For a temporary stop, set 'Enabled for users to sign in' = No (deactivate) instead of deleting. |
| Choosing the CA session control 'Use app enforced restrictions' to block downloads from a third-party SaaS app such as Salesforce or Box on unmanaged devices. | App-enforced restrictions only work for apps that understand the device claim — SharePoint Online, Exchange Online, M365 idle-session timeout. Third-party SAML/OIDC apps need 'Use Conditional Access App Control' with a Defender for Cloud Apps session policy (Block download). Native-client blocking needs an access policy. |
| 'Configure the federated credential subject as repo:contoso/app:ref:refs/heads/*' or trusting that the credential saved successfully means it is correct; or using the App registrations Object ID in a workload-identity CA policy. | Wildcards and pattern matching are not supported; subject must match the GitHub token's sub exactly (use Environment entity when a workflow runs on many branches; a pull_request-triggered job needs the Pull request entity). A wrong subject is accepted at save time and only fails silently at exchange. CA for workload identities needs the service principal Object ID from Enterprise apps, not the App registrations Object ID. |

## D4 — Plan and automate identity governance · 20-25%

> ⚠ **Sourced differently from D1-D3.** The research agent that owned this domain was killed
> by a monthly spend limit partway through the run. These pairs are written from the live
> skill groups and standard SC-300 material rather than fetched and link-verified one by one,
> so treat the *distinctions* as reliable and **verify any specific number against Microsoft**
> **Learn before quoting it.** The four live skill groups are: entitlement management · access
> reviews · privileged access (PIM) · **monitor identity activity using logs, workbooks and reports**.

### Discriminators

**PIM **eligible**** vs **PIM **active****
- Eligible means the assignment exists but the privilege is not held until the user activates it, with whatever activation controls the role requires. Active means they hold it right now. Both can additionally be permanent or time-bound, giving a 2x2.
- **Tell:** 'just-in-time', 'only when needed', 'must request', 'approval before use' -> eligible. 'standing access', 'holds the role continuously', 'break-glass' -> active (and usually permanent).

**PIM for **Entra roles**** vs **PIM for **Azure resources****
- Two separate blades with separate assignment stores. Entra roles govern the directory (Global Admin, User Admin). Azure resource roles govern subscriptions/resource groups via Azure RBAC (Owner, Contributor).
- **Tell:** 'Global Administrator', 'User Administrator', 'directory role' -> Entra roles. 'subscription', 'resource group', 'Owner on the production subscription' -> Azure resources.

**PIM for **Groups**** vs **Role-assignable group**
- PIM for Groups makes *membership or ownership of a group* eligible/active. A role-assignable group is a group that can have a directory role assigned to it at all. They compose: make a group role-assignable, assign it a role, then use PIM for Groups so membership is JIT.
- **Tell:** 'activate membership', 'eligible member of the group' -> PIM for Groups. 'assign a role to a group' -> role-assignable group.

****Access review**** vs ****Entitlement management****
- A review *certifies access that already exists* and produces an approve/deny decision. Entitlement management *grants access in the first place*, packaged as a catalog + access package + policy, with a request, approval and expiry.
- **Tell:** 'recertify', 'confirm they still need it', 'quarterly attestation' -> access review. 'request access', 'self-service', 'bundle of resources', 'time-limited assignment', 'external partner requests' -> entitlement management.

****Access package**** vs ****Catalog****
- A catalog is the container of resources (groups, apps, SharePoint sites) that can be offered. An access package is a bundle of some of those resources plus one or more policies saying who may request it and on what terms.
- **Tell:** 'group resources so a department owner can manage them' -> catalog. 'what the requester actually receives' -> access package.

**Entitlement-management **policy**** vs **Conditional Access policy**
- In entitlement management, 'policy' means *who may request this package, who approves, how long it lasts*. It has nothing to do with sign-in conditions.
- **Tell:** If the stem is about requesting and approving access -> EM policy. If it is about a sign-in being allowed or blocked -> CA.

****Connected organization**** vs **B2B guest / external collaboration settings**
- A connected organization is an entitlement-management object that names an external tenant or domain so its users can *request* access packages. External collaboration settings decide who may *invite* guests at all; cross-tenant access settings decide trust.
- **Tell:** 'partner organization should be able to request access to the package' -> connected organization. 'who can invite guests' -> external collaboration settings. 'trust their MFA / accept their compliant device' -> cross-tenant access settings.

**Access review **for guests**** vs **Inactive-guest insights**
- A review decides per-guest whether access continues. Inactive-guest insights surface guests with no recent sign-in and are an Entra ID Governance SKU feature, not plain P2.
- **Tell:** 'has not signed in for 90 days, report it' -> inactive guest insights (and note the licence). 'reviewer decides' -> access review.

**Reviewer = **self**** vs **Reviewer = manager / group owner / selected users**
- Self-review asks the user to attest to their own access. The others put the decision with someone accountable. The exam likes self-review for large guest populations and manager review for employees.
- **Tell:** 'ask the users themselves to confirm' -> self. 'their manager should decide' -> manager. 'the group owner' -> group owner.

****If reviewers don't respond**** vs **Auto-apply results**
- Two different settings. 'If reviewers don't respond' sets the *decision* for un-actioned items (No change / Remove access / Approve access / Take recommendations). 'Auto apply results to resource' controls whether decisions are *enforced* automatically when the review ends.
- **Tell:** 'nobody responded, what happens to their access' -> the don't-respond action. 'decisions must take effect without an admin clicking Apply' -> auto-apply.

****Lifecycle workflows**** vs **Entitlement management**
- Lifecycle workflows automate *joiner/mover/leaver tasks* triggered by attributes such as employeeHireDate and employeeLeaveDateTime. Entitlement management is request-driven. Lifecycle workflows need the Entra ID Governance SKU, not P2.
- **Tell:** '30 days before the hire date, generate a TAP and email the manager' -> lifecycle workflow. 'user asks for access to a package' -> entitlement management.

****Separation of duties**** vs **Incompatible access package**
- In entitlement management you can mark two access packages incompatible, so holding one blocks requesting the other. That is the concrete implementation of separation of duties.
- **Tell:** 'a user who has Finance-Approver must not be able to get Finance-Payments' -> incompatible access packages.

****Sign-in logs**** vs ****Audit logs****
- Sign-in logs record authentication events (who signed in, from where, which app, CA result). Audit logs record *changes to the directory* (who created the user, who changed the policy).
- **Tell:** 'which policy applied to this sign-in' / 'why was this blocked' -> sign-in logs. 'who deleted the group' / 'who changed the CA policy' -> audit logs.

****Provisioning logs**** vs **Audit logs**
- Provisioning logs are specific to SCIM/app provisioning and HR-driven inbound provisioning - what was created, updated or skipped in the target app and why.
- **Tell:** 'why was this user not created in ServiceNow' -> provisioning logs.

**Log **retention in Entra**** vs **Diagnostic settings to Log Analytics**
- Entra retains sign-in and audit logs for a limited window by licence (7 days free, 30 days with P1/P2). To keep them longer or query them with KQL you send them via diagnostic settings to a Log Analytics workspace, a storage account, or an Event Hub.
- **Tell:** 'keep for a year', 'run a KQL query', 'build a workbook' -> diagnostic settings + Log Analytics. 'need it right now for last week' -> the portal logs.

****Workbook**** vs **Usage and insights report**
- Workbooks are customisable KQL-backed reports over the Log Analytics data. Usage and insights are Microsoft's pre-built application/sign-in reports inside Entra.
- **Tell:** 'custom visualisation, our own query' -> workbook. 'which apps are used most' -> usage and insights.

****Identity Secure Score**** vs **Microsoft Secure Score**
- Identity Secure Score is the identity-only percentage inside Entra with improvement actions. Microsoft Secure Score is the wider M365 posture score across identity, devices, apps and data.
- **Tell:** If the stem is only about Entra ID posture -> Identity Secure Score.

****Privileged Role Administrator**** vs **Global Administrator**
- Privileged Role Administrator can manage role assignments and configure PIM - which is everything PIM questions need - without being Global Admin. Least privilege means it is almost always the right answer.
- **Tell:** 'configure PIM settings', 'assign directory roles', 'least privileged' -> Privileged Role Administrator.

****Identity Governance Administrator**** vs **User Administrator**
- Identity Governance Administrator owns access packages, access reviews and lifecycle workflows. User Administrator manages users and groups and cannot configure governance.
- **Tell:** 'create the catalog / access package / review' -> Identity Governance Administrator.

****Approval** in PIM activation** vs ****Justification** and **MFA** in PIM activation**
- Three independent activation controls per role: require justification (free text), require MFA on activation, require approval (names approvers). Maximum activation duration is set separately.
- **Tell:** 'someone must sign off before the role becomes active' -> require approval. 'must state why' -> justification.

### Traps

| The wrong answer that looks right | Why it is wrong |
|---|---|
| Answering 'access review' when the stem describes granting new access to an external partner. | Granting is entitlement management: a catalog, an access package, a policy, and a connected organization for the partner. Reviews only certify access that already exists. |
| Assuming lifecycle workflows are included in Entra ID P2. | They require the Microsoft Entra ID Governance SKU. Microsoft has said no new governance features will be added to P2. If the stem says 'we have P2' and asks for automated joiner tasks, check whether Governance is stated. |
| Choosing Global Administrator for a PIM configuration task. | Privileged Role Administrator is sufficient and is the least-privileged answer. Global Admin is offered specifically to catch the reflex. |
| Thinking eligible assignments survive a licence lapse. | When P2 lapses, eligible assignments are removed and time-bound active assignments become permanent. This is a real security event, and it happened in your own tenant on 2026-09-10. |
| Treating 'auto apply results' and 'if reviewers don't respond' as the same setting. | They are independent. A review can decide 'Remove access' for non-responses and still not enforce it until an admin applies the results, if auto-apply is off. |
| Reaching for Log Analytics when the question only needs the portal. | If the data is inside the retention window and no custom query is required, the answer is the sign-in or audit log blade. Diagnostic settings are the answer when the stem says long retention, KQL, workbooks, or SIEM. |
| Confusing the review scope 'Everyone' with 'Guest users only'. | Guest-only reviews are the standard pattern for external access recertification and are frequently the intended answer when the stem mentions partners. |
| Assuming PIM covers group membership by default. | That is PIM for Groups, configured separately, and the group must be role-assignable if a directory role is attached to it. |
